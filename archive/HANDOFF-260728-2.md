## ⚠️ The thing actually worth carrying: getting the files in

The wire-in was routine. **Transport took four attempts and most of the
session.** Recorded so nobody re-runs it:

1. **Dropbox Transfer (`dropbox.com/t/...`) — impossible headlessly.** The file
   list is fetched by JS after load; the download sits behind an undocumented
   internal API. Every guessed endpoint 404s. A Transfer link is *not* a
   share link.
2. **Chromium cannot reach the network through the agent proxy.** Even
   `example.com` → `ERR_CONNECTION_RESET`, and the proxy records **no**
   failure for it. So "drive it in a real browser" is not a fallback in this
   environment. Don't spend time there.
3. **A corporate SharePoint link is an identity boundary, not a format
   problem.** `tishman-my.sharepoint.com` issued **zero** cookies on
   redemption; Graph returned **401 "Access token is empty"**;
   `api.onedrive.com` returned **"User migrated"**. It works for the owner
   only because their browser is already signed in to their work tenant.
   **Do not try to route around it** — ask for a personal account. Changing
   the `?e=` token changes nothing; it is a tracking param, not a key.
4. **What worked: attaching the MP3s in chat.** They land in
   `/root/.claude/uploads/<session>/` with a random hex prefix per file.

**Lead with the chat attachment for any batch of 20–60 files.** It needs no
link, no sharing settings, and cannot be blocked by the owner's IT policy. I
burned three rounds on share links before saying so plainly.

## ⚠️ gh-pages Pages deploy lagged the push by ~10 minutes

Both audio pushes served **404 for roughly ten minutes** after a successful
push, with the deploy sitting `in_progress`. This is exactly the trap
CLAUDE.md flags: **verify the live URL (and its hash), never the push.**
Merging during that window would have shipped tours with dead audio, since
content reaches users over the air with no app build.
