## The question

Owner forwarded a Supabase email: the org had exceeded its plan quota, Fair Use grace period to
**4 October 2026**, *"reduce your egress bandwidth below 5.5 GB."* They asked three things in
sequence — is this growth or waste, should we cache more, and what does a fix save.

## What was measured, not guessed

`get_catalog()` returns the entire catalogue in one document. Measured live against the RPC:

* **10,991,263 bytes raw · 3,622,909 bytes gzipped**, byte-identical content (sha256 matched).
* Field breakdown of the minified payload: `stops.transcriptText` **38.0%**, `longDescription`
  **18.3%** — **56% of every fetch is text visible only on one tour's detail page.**
* It is a **POST RPC**, so there is no ETag, no `If-None-Match`, no 304. **A fetch that finds
  nothing new costs exactly as much as one that finds a whole new city.** This is the fact the
  whole problem rests on, and it is structural, not a bug.

Stripping `transcriptText` alone would take the payload to 1.61 MB (−41%); both heavy fields,
0.87 MB (−68%). Both are breaking catalogue changes and were deliberately not attempted.

## 🔴 The finding: the biggest consumer was our own tooling, not the app

`scripts/session-start.sh` sampled `get_catalog` **four times per session** purely to read an
HTTP status code, discarding every byte to `/dev/null`. That is **~44 MB of Supabase egress at
the start of every session**, and the script runs by automation rule #1 on every session,
including the parallel ones that run several times a day.

It now sends `--compressed --max-filesize 2000`: **8,000 bytes for the same four samples**, a
5,500× cut, and it still prints the same `4/4 OK`.

**The detection it exists for was verified intact rather than assumed.** Across six live samples
five returned `http=200` with real catalogue JSON and one returned `http=500` carrying
`{"code":"57014","message":"canceling statement due to statement timeout"}` — the documented
flakiness, caught exactly as before, because the status arrives in the headers ahead of the body.
⚠️ **curl exits 63 on the success path here**; the check reads `%{http_code}`, which is unaffected.
A comment at the call site says so, because the obvious "tidy-up" is to delete those flags.

## ⚠️ A claim I made to the owner and then had to correct

I told them I would convert `check-catalog-keys.py` and `check-catalog-contract.py` to the
**47-byte count query**. **That was wrong and I said so plainly before doing it.** Both scripts
read keys off the first row of each collection and sweep every tour for stray link pins — they
genuinely need the whole payload, and a count query cannot replace them.

What they were actually doing wrong is smaller and real: **neither asked for compression.**
`curl` needs `--compressed`; `urllib` needs an explicit `Accept-Encoding: gzip` **and** a
`gzip.decompress` on the way back (guarded on the response's own `Content-Encoding`, since asking
is not the same as receiving). ~10.5 MB → ~3.5 MB per run for byte-identical JSON, and
`contract.py`'s retry loop could otherwise triple it.

**The durable lesson: check what a proposed fix actually needs before promising it.** The count
query is genuinely useful — it is now documented — but not for these two callers.

## Also changed

`DataService.foregroundRefreshInterval` **60 s → 900 s**. Sixty seconds meant glancing at a map
and returning re-downloaded the entire catalogue, which itself changes two or three times a day.
A cold launch always refreshes regardless (`autoRefresh` in `init`), so this governs
background→foreground returns only. The debounce unit test injects its own interval and needed no
change. The init's doc comment now explains that it is an **egress dial, not a freshness dial**.

## 🔴 What this does NOT fix — the number that matters

Raising the debounce **buys time; it does not scale.** The catalogue changes ~70×/month, so a
daily user meets a changed catalogue on nearly every launch and **still pays the full 3.4 MB** —
roughly **240 MB per active user per month as a floor**. About **20 active users** puts the
project back over quota with this already merged.

The durable fix is a cheap **`catalog_version()`** RPC the app calls before deciding to download
anything, then delta (`?since=<version>`) or city-scoped fetching. **Neither is built.** It
touches the database and the app's launch path, so it wants writing up and reviewing before it is
built — the owner has been told exactly that.

⚠️ **The baseline is inferred, not observed.** The Supabase Usage dashboard holds the real split
between our tooling, the owner's device testing and any real users; no session can see it. The
~5 GB → under 0.5 GB estimate is arithmetic over measured payload sizes and session counts, and
should be checked against the dashboard once a billing period has passed under the new numbers.
