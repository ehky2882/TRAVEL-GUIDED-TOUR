# HANDOFF 2026-09-09 (2) — signup emails come from Dozent

**Owner:** *"When a user signs up for an account via the email method they get a confirmation email
from supabase. If they're unfamiliar with it they don't know if it's legitimate. Is there a way to
have an email come from dozent or be branded that way?"* Then: *"yes, walk me through it extremely
simply."*

Shipped as [#771](https://github.com/ehky2882/TRAVEL-GUIDED-TOUR/pull/771) (squash `6fbdc07`).
Two files; no Swift, no `Tours.json`, no SQL. Most of the work was dashboard configuration, which
is why it is written down here.

## What it was

Confirmation emails came from **"Supabase Auth"** with a *"powered by Supabase ⚡"* footer. Beyond
looking untrustworthy, Supabase's built-in sender is documented as development-only and
rate-limited, so it would have started silently dropping signup emails at real volume — it needed
replacing before launch regardless of branding.

## 🔴 THE BUG THAT COST FIVE TEST SIGNUPS, AND IT WAS MINE

Every click returned `otp_expired` — *"Email link is invalid or has expired"* — and no account
ever confirmed. Four rounds went into scanner theories, link-prefetch theories and expiry
theories, all wrong.

**The cause: the emails contained `token=EXAMPLE`.** I had sent the owner a *rendered preview* of
the template (via `SendUserFile`) **before** the paste-ready code, and the preview had the
placeholder baked in where `{{ .ConfirmationURL }}` belongs. The preview was the more
obvious-looking thing to copy, so it is what got pasted into Supabase.

**What settled it:** the owner pasted the link, it read `token=EXAMPLE`, and fetching it from this
container reproduced their error URL **character for character**, including the trailing `&sb=`.

```
$ curl -sS -o /dev/null -w '%{redirect_url}' \
    "https://<ref>.supabase.co/auth/v1/verify?token=EXAMPLE&type=signup"
https://dozent.world/confirmed/#error=access_denied&error_code=otp_expired&...&sb=
```

**⚠️ Never ship a rendered preview alongside a paste-ready template.** If a preview is wanted,
make its placeholder unmistakable (`PASTE_ERROR_IF_YOU_SEE_THIS`) or send only the real thing.

**⚠️ Verify a confirmation by asking the database, not by looking at the page.** The final click
looked like a failure — the screenshot showed `otp_expired` — while the account was in fact
confirmed: the first click had spent the single-use token successfully and the screenshot was a
repeat. The check that settled it needs only the publishable key:

```bash
curl -sS -X POST "https://<ref>.supabase.co/auth/v1/token?grant_type=password" \
  -H "apikey: <publishable>" -H "Content-Type: application/json" \
  -d '{"email":"...","password":"..."}'
# access_token present = confirmed;  email_not_confirmed = not
```

## Decisions

**The `send.` subdomain over the apex, deliberately.** `dozent.world` already carries ImprovMX's
MX records and an SPF record, and **only one SPF record is permitted per name** — verifying the
apex would have meant merging them and risking the `hello@dozent.world` forwarding. Cost, stated:
mail sends from `noreply@send.dozent.world`. The display name "Dozent" is what an inbox shows.

⚠️ **Resend registers a `send.` bounce subdomain on top of whatever you give it**, so the records
read `send.send.dozent.world`. Not a mistake.

**DMARC was added after the first email landed in spam.** Resend marks it *(Optional)* and I
initially told the owner to skip it — wrong. Gmail has expected it since 2024, and its absence on
a new domain pushes hard toward spam. Scoped to `_dmarc.send.dozent.world` with `p=none`
(monitor-only), so the apex is untouched. Verified live:

```bash
curl -sS "https://dns.google/resolve?name=_dmarc.send.dozent.world&type=TXT"
```

**Resend's "Auto configure" button does the whole Vercel DNS step.** It shows exactly which
records it will create — all three on the `send.` branch, creations only — so the apex MX and SPF
cannot be touched. Far better than hand-typing records with a non-technical owner.

## The template and the landing page

`backend/email-templates/confirm-signup.html` — brass on black, ported from `site/atlas.css`. Two
constraints are load-bearing: **no images anywhere** (clients block remote images by default, so a
logo would be a broken box exactly where the brand mark belongs) and the **button is a `bgcolor`
on a `<td>` with padding on the `<a>`** (Outlook Windows drops padding from a styled `<a>`).

`site/confirmed/index.html` — **two states, because Supabase serves both from one URL.** Failure
appends to the **fragment** (`#error=access_denied&error_code=otp_expired`), so a page that only
said "Email confirmed" would lie at exactly the wrong moment. The fragment is read, never echoed:
only the presence of `error` is acted on, and `error_description` is deliberately not rendered —
it is attacker-controllable text in the URL. Footer byte-identical to the other five pages
(verified by hash); `noindex`; deliberately **not** added to the footer link row.
