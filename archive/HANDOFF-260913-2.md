## The cause, and the three traps beside it (#852)

A cloud environment starts on the **Trusted** network access level: package registries and GitHub,
nothing else. The pin pipeline needs `tiktok.com`, `instagram.com` and `ehky2882.github.io`.

**Why it is dangerous rather than merely annoying:** GitHub *is* reachable, so everything except
the thumbnail works. The batch fails **half done**, with `Tours.json` already pointing at hero
files nobody uploaded — which `validate-tours.swift` passes, because the URLs are well-formed and
it never fetches them. And it is not an edge case: link pins are the first job a new contributor
does, so it fires on batch one for everyone.

Fix: claude.ai/code → the cloud icon above the message box → settings → **Network access:
Trusted → Full** → **a new session** (an open one keeps the old setting).

Three neighbours, all found the same day and all now in `docs/lessons.md`:

- **Pillow is often absent**, and without it `make-link-pin.py --selftest` reports **62/62, which
  reads as a pass**, against **71/71** with it. It silently skips the whole image path.
- **`gh` may be absent too**, and the obvious workaround is itself the trap. 🔴 **A checkout of
  gh-pages killed partway left a tree where `git add` staged 9,430 deletions.** Committing it
  would have wiped thousands of live images. It was caught only by reading the tree diff before
  pushing. Build the commit with plumbing instead — `read-tree` → `update-index` → `write-tree` →
  `commit-tree` → push a ref — which is also the one-rebuild property `upload-images.py` protects.
- **`check-image-duplicates.py --pins` printed `OK — no suspicious duplicates` having 404'd on
  every new hero**, because a Pages deploy takes ~10 minutes. § "Knowing whether a check actually
  ran", in a fresh costume.
