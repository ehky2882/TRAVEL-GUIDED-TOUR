## ⚠️ The owner was right and I was wrong — worth remembering

I argued against putting a pannable map inside a `ScrollView`, on the grounds
that the map and the page would fight for the drag. The owner pointed out that
**tour detail already does exactly this**, and it has shipped for months.

`TourDetailView.mapContent` — 320pt (`AtlasSpacing.heroHeight`), inset 24pt
(`AtlasSpacing.lg`), square corners, inside the scrolling body. **The 24pt
gutters either side are the whole trick**: they're where a drag scrolls the page
instead of panning the map. That inset is load-bearing, not decoration.

The lesson is procedural, not technical: **check whether the codebase has already
solved the problem before reasoning about whether it can be solved.** A working
screen beats an argument.

### The pin extraction fixed a live drift

`TourDetailView` had **reimplemented** `StopPin` and `UserLocationDot` by hand,
with a comment saying it had to because the originals were `private` to
`HomeMapSection`. The copies had already diverged — a **14pt dot there against
Home's 16pt**. The maker map would have been the third copy. All three now come
from one file and the drift is fixed as a side effect.

**Durable rule: a `private` view that another screen visibly needs is a latent
duplicate.** The comment admitting the copy sat in the codebase for weeks.

### Deleting the segmented controls deleted more than expected

Both call sites reached into **`UISegmentedControl.appearance()`** to force SF
Mono onto their labels. That's a **global** proxy mutation — it was restyling
every segmented control the app could ever show, including inside system sheets,
to serve two pickers. Both are gone.

`TourDetailView.init(tour:)` went with them: it existed *only* to run that hack,
and had to duplicate `LibraryView.init`'s copy because a cold launch straight
into a tour would otherwise render before Library was ever instantiated. **No
proxy, no ordering bug, no init.**

### `cellsAcross` is now a parameter

It counts cells across the **region**, not the screen. At 320pt tall the home
map's 20 cells span far fewer points, so visually adjacent pins refuse to merge.
The maker map passes 12.

## 🐛 A bug the compiler couldn't catch, found by re-reading after CI went green

The camera and the clustering region were seeded in **two different `.task`
blocks** — the parent set `mapCamera`, the map seeded `currentRegion` from
`cameraPosition.region`. Whichever ran first, the camera was still `.automatic`
(region `nil`) when the seed read it, so `currentRegion` stayed nil.

Clustering falls back to "every marker is a single" with no region, and `.onEnd`
doesn't fire until the user moves the map — which on this screen they may never
do. **A maker with 40 tours in one city would have opened to a pile of
overlapping dots and stayed that way.** Fixed in `6f31c7a`:
`MakerMapSection` takes `initialRegion` and sets both in one place.

**Two `.task` blocks that must agree are a race.** The build was green either way.

## ⚠️ Scope I could not deliver, and why

The owner asked for **all three tabs on every maker page**. **LISTS is
own-profile only.**

Reading another creator's public lists means querying `journeys` by
`owner_user_id` — an `auth.users` id. `makers.user_id` exists in the database but
**`get_catalog()` never emits it**, so the client's `Maker` model has no
`userId`. That is a backend change, and Pass 1 was scoped as no-SQL.

I had earlier told the owner this needed no backend work. **That was wrong** — I
took `userId` from an exploration report describing `MakerRow`, the private
Supabase DTO inside `MakerProfileService`, not the `Maker` the app actually
renders. Corrected before any code depended on it.

It belongs with the visibility model anyway (below), since both need the same
backend pass. `availableTabs` narrows the strip; an `onChange` moves the user off
a tab that disappears.

## Owner's list-visibility model — decided, designed, not yet built

*"if a maker is public then everything is public. if maker is private but you are
friends then you should be able to see your friend's list. unlike there is a
subset of private lists that even your friend's can't see."*

**A list is Shared or Only me.** Who "Shared" reaches is decided by the account,
not the list: public account → anyone; private account → accepted followers.
"Only me" is invisible to everyone, followers included. Two states on the list;
the existing account switch does the rest.

### Two schema traps recorded so they aren't rediscovered

- **`follows.followee_id` is a MAKER id; `journeys.owner_user_id` is an AUTH USER
  id.** The bridge is `makers.user_id`, unique only via a **partial** index
  (`accounts.sql:118-120`) — the 19 Atlas studios all carry `user_id = NULL`.
  Join as `m.user_id = j.owner_user_id` and never let NULL match, or **every seed
  studio matches at once**.
- **`makers.user_id` is `on delete set null` while `journeys.owner_user_id` is
  `on delete cascade`** — a deleted user's lists vanish but their maker row is
  orphaned. Treat "no maker row" as not-private.

No helper answers "can viewer X see maker Y's content" today. `list_followers` /
`list_following` inline a *strictly-owner* rule that ignores `follows` entirely,
copy-pasted in two places. A new SECURITY DEFINER `can_view_user(u uuid)` should
own the hop so no RLS policy has to inline it.

**Migration note:** `is_public boolean default false` becomes the two-state
field. Write `true → Shared` as an explicit mapping, not a rename.

## ⚠️ "Private should hide everything" — decided late in the session, bigger than it sounds

The owner was confused by my explanation of why lists couldn't show on other
people's pages, and said so: *"i'm really not understanding what you're saying."*
**That was my failure, not theirs.** I kept saying "backend change" when the
honest sentence was: *the app has to ask the database for "this person's lists",
and the creator profile it's holding doesn't contain the person's account ID, so
it can't name who it means.* One line of SQL and one field on a struct.

Two things came out of clearing that up.

**1. The owner thought per-list privacy wasn't built. It is.**
`TourListEditorSheet` has a Public toggle and `journeys.is_public` **defaults to
false**, so every list today is already private. Once public reads work, a
stranger sees an **empty** Lists tab until the owner deliberately toggles
something on. State that before describing plumbing.

**2. Owner: "private should hide everything" — lists, tours, the lot.**

⚠️ **This collides with the catalog's architecture.** `Tours.json` /
`get_catalog()` is **one public payload with no viewer** — every phone fetches
the same bytes, caches them, and falls back to a gh-pages mirror then a bundled
seed. Making a private maker's tours invisible means the payload must differ per
person, which that design cannot do.

| Option | Verdict |
|---|---|
| Drop private makers' tours from the catalog | Trivial, but their own accepted followers lose them too — not what was described |
| Per-viewer catalog via authenticated RPC | **Don't.** Kills anonymous browsing, the offline cache and the gh-pages fallback; auth on every cold launch |
| **Hybrid** — public catalog excludes private makers, a second authenticated call fetches tours from private makers you follow, merged client-side | **Right shape.** Keeps cache, mirror and anonymous browsing; one extra call when signed in |

Also: `get_catalog()` emits the **maker row** to everyone, so "hide everything"
means hiding the profile from search and the map, not just its tours. **Its own
project — do not bolt it onto the lists work.**

**Agreed sequencing:** public lists on other maker pages ship **next** (one
`get_catalog` line emitting `user_id`, a `Maker.userId` field,
`publicLists(ofUser:)`) alongside the Shared / Only-me model, since both need the
same SQL trip. Private-hides-everything is scoped separately, after.
