## The answer to the question as asked — and why the obvious fix is wrong

**We do preload.** `LaunchImageWarmup` fetches the first **8** hero images
before hand-off. But it gives up after **1.2 s**, inside a **3.0 s** gate
ceiling, and on a weak connection neither is enough for a single photograph. So
nothing warmed and the splash handed off as designed.

**🔴 DO NOT MAKE THE SPLASH WAIT FOR "EVERYTHING LOADED". It is the intuitive
fix and it is the wrong one:** with no signal that condition may never be met,
and the splash then reads as a frozen app. The ceiling exists precisely to stop
that (`LaunchGate`'s own doc comment says so). Everything except photographs
already works with no signal — catalogue, map, titles, distances, downloaded
audio. Extending the deadline would also slow every good-signal launch to buy
nothing on a bad one.

## The real cause, measured

**GitHub Pages serves photographs with `Cache-Control: max-age=600`.**

```
$ curl -sI https://ehky2882.github.io/TRAVEL-GUIDED-TOUR/images/times-square-from-tkts-hero.jpg
cache-control: max-age=600
```

`App.init` sets a **200 MB** `URLCache`, so the bytes are on the phone — but
after **ten minutes** iOS treats the entry as stale and must revalidate with the
server before using it. Underground there is no server, the request fails, and
the photograph is not drawn **even though it is sitting on disk**. The storage
was working; the freshness rule threw the result away.

That is two separate gaps, and this branch closes the first.

## Shipped here: a downloaded tour brings its photographs

**🔴 `TourDownloader` QUEUED THE INTRO AUDIO AND EACH STOP'S AUDIO AND NOTHING
ELSE** — so a tour deliberately saved for a journey with no signal had no
pictures at all. Now `TourDownloader.downloadPlan(for:)` (a pure static, so it
is testable without a network) queues the hero and every stop photograph too.

- **⚠️ The files go in the tour's own folder** (`Documents/atlas-tours/<id>/`),
  beside its audio — **not** in `URLCache` or `ImageCache`. Both of those are
  caches in the real sense: the system evicts them, and **Settings → Clear Cache
  empties them** (verified: it calls `URLCache.removeAllCachedResponses()` and
  `ImageCache.shared.clear()`, and does not touch `atlas-tours`). Neither should
  be able to strip the pictures off a tour the user explicitly saved. Deleting
  the download still removes them, because it removes the folder.
- **⚠️ AUDIO IS QUEUED FIRST, deliberately.** Files download sequentially, so a
  download interrupted half way still yields a tour you can *listen* to.
- **⚠️ Deduplicated by URL, and that is not a micro-optimisation:** a
  single-stop tour sets `stop0.imageURL` to its own hero and a walk's intro stop
  reuses the landmark's photograph, so the naive list repeats constantly — and
  two files of identical bytes under one name would make the progress total lie.
- **`additionalImageURLs` are deliberately excluded** — browsing material, seen
  before you set off, and they would roughly double the download.
- **🔴 THE LOOKUP HAS TO WORK FROM A URL ALONE**, because `HeroImageView` is
  handed an image URL and knows nothing about which tour it belongs to. So the
  files are named `img-<sha256 prefix>` after their own URL, and
  `Data/DownloadedImageIndex.swift` maps that back to the file.
  **⚠️ It is a shared instance rather than an `@Environment` value on purpose:**
  `HeroImageView` renders inside the UIKit slide-up layers, which do not inherit
  the SwiftUI environment, and a dropped injection there would show up as
  *photographs silently missing offline on exactly the screen that matters*.
  **⚠️ It is deliberately not `@MainActor`** — `TourDownloader` is not
  actor-isolated (its delegate callbacks merely arrive on the main queue), so
  main-actor isolation does not compile at the call sites and
  `MainActor.assumeIsolated` would be an assertion about someone else's
  threading. An `NSLock` is the honest guarantee.
- `HeroImageView.fetchIfNeeded` reads the downloaded copy **before** touching
  the network.

### Verified end to end, not just unit-tested

In the Simulator: downloaded a tour, then confirmed on disk —

```
8CFBEBAD-…/img-e07fcde693690a69.jpg   508,802 bytes
8CFBEBAD-…/681D1D59-….mp3           1,909,293 bytes
```

one photograph, not two, for a single-stop tour whose hero and stop image are
the same URL. Then **relaunched** (which empties the in-memory cache) and opened
the tour with a temporary probe in the local branch: it logged
`served from downloaded copy: img-e07fcde693690a69.jpg` **exactly once** — the
downloaded tour, with every other card still going to the network. Probe removed
before committing.

## Still open — the second gap

**When a photograph has been seen before but the network is unavailable, fall
back to the disk copy instead of failing.** Try the network as normal; on
failure read `URLCache.shared.cachedResponse(for:)` rather than showing grey.

**⚠️ Owner has approved the trade-off in principle** (2026-08-23): offline you
may see a photograph we have since replaced — as with the Thyssen mix-up — until
you are back on signal. Bounding the fallback to *actual request failure* keeps
that exposure to the offline case only; a blanket `.returnCacheDataElseLoad`
would freeze photographs permanently and must not be used.

Smaller, also open: say "you're offline" rather than showing blank grey.
