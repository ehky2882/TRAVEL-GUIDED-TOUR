## Why it did nothing (#423)

Root causes, all in the discovery/connection layer:

1. **Silent discovery failure — the headline.** `MultipeerTransport` implemented
   neither `didNotStartAdvertisingPeer` nor `didNotStartBrowsingForPeers`, and the
   coordinator exposed no connection state. A denied **Local Network** permission
   (or simply no peer in range) left both phones showing a code/roster forever with
   zero feedback. Added both delegates plus `GroupConnectionStatus`
   (idle/searching/connected/failed) surfaced through transport → coordinator →
   sheet + banner, with actionable Settings copy.
2. **False "Leader left."** `onLeaderLost` fired during the initial handshake (a
   peer going `.connecting → .notConnected` before ever connecting) and on any
   transient blip — pausing audio and flashing the red banner on a working session.
   Now gated on `everConnected`.
3. **Epoch poisoning.** `sessionEpoch` was a monotonic per-device counter never
   reset, so a phone that had *led* a session could, when it later *joined* as a
   follower, permanently ignore a fresh leader's lower-epoch broadcasts
   ("connected, roster shows 2, no audio"). Reset on `join()`/`leave()`.
4. **Intro-audio desync.** A leader playing the tour intro broadcast `stopIndex 0`,
   so followers played stop 0 over the intro. Added `GroupPlaybackState.isIntro`.
5. **Data race** on `peerParticipants` (mutated from arbitrary MPC delegate queues).

**Honesty fix:** the sheet claimed "Works offline over Bluetooth," but **audio is
never sent peer-to-peer** — only the tiny state packet is. Each follower fetches
the MP3 itself, so an un-downloaded tour with no signal connects fine and plays
nothing. Copy corrected; a `followerAudioFailed` state now surfaces it.

## Sync tightening (#428)

Owner on the first working build: *"not perfectly in sync."* That was v1 tuning,
not a bug — followers tolerated **1.25 s** of drift (3–4 spoken words) before doing
anything, and the threshold couldn't simply be lowered because every correction was
a hard seek, which is audible. Replaced with **two-tier correction**:

| drift | action |
|---|---|
| `< 0.15 s` | leave alone |
| `0.15–2.0 s` | trim playback speed up to **3%** — glides back inaudibly |
| `≥ 2.0 s` | precise seek (stall / late joiner) |

- `AudioPlayerService` gains **`syncTrim`**, deliberately separate from the
  user-facing `rate` so the speed menu never lies and **solo playback is
  unchanged** (trim 1.0 → `effectiveRate == rate`). Cleared in `stop()` and on
  `leave()` so a trim can never leak into solo playback.
- **`seek(to:precise:)`** — sync corrections use zero tolerance; the default can
  land a few hundred ms off and silently reintroduce the drift it was fixing.
  Scrubbing keeps the tolerant path.
- Heartbeat **1.0 s → 0.5 s**.
- `sentAt` latency compensation still deliberately unused — Multipeer latency
  (~10–50 ms) is inside the dead zone and cross-device clock skew would be a net loss.

**Owner verdict: "good enough to ship."** Do not spend more here without a new
complaint. Remaining levers if ever needed, in order: lower `driftDeadZone`,
shorten `heartbeatSeconds`, widen the ±3% band
(`AudioPlayerService.min/maxSyncTrim`). **Genuinely tighter than ~a couple hundred
ms is an architecture change, not tuning** — shared-clock scheduled playback
(AirPlay 2 / Sonos / `AVPlaybackCoordinator`), not more aggressive correction.

## QR joining (#428)

Deferred design item (§6) — owner asked for it "in addition to the character code."

- Leader shows a scannable QR **above** the 5 characters (kept as fallback).
  Generated with **Core Image**'s built-in filter — no new dependency.
- Joiner screen leads with **Scan QR code**, manual entry under "or type it".
  `QRScannerView` (AVFoundation, `.qr` metadata only) handles the states that would
  otherwise look broken: permission denied (with the Settings path) and **no camera
  at all (the Simulator)**.
- The QR encodes the **https Universal Link** (`…/g/?code=XXXXX`), not a bare
  string, so the **system Camera app** also works and it degrades to the web page if
  the app isn't installed. `DeepLink` gains `.group(code)`; the App joins directly
  (no tour id needed — the leader broadcasts the tour) and toasts if signed out.
- Codes are validated on the way in (exact length, alphabet-only), so an unrelated
  QR — or one of our own *tour* share links — is ignored rather than starting a
  session that could never connect.
- Adds **`NSCameraUsageDescription`** (mandatory before any camera use).

## The untappable banner (#428)

Owner: the session banner's **Leave button did nothing**. Not the button — **hit
testing**. The banner renders in the secondary higher-level window, whose
`PassThroughWindow.hitTest` returned `nil` above a **fixed 126 pt strip**
(`AtlasBottomModule.height()` = mini-player + tab bar) set once at install. The
banner sits *above* the mini-player, so every touch passed through to the main
window. It drew fine (drawing doesn't consult hit-testing) but could never be
tapped.

**Fix (general, not special-cased):** `BottomModuleRoot` measures its real painted
stack via `onGeometryChange` and reports it; new
`BottomModuleWindowController.setInteractiveBottomInset(_:)` applies it. Anything
added above the mini-player in future is now tappable automatically.

## The Apple certificate cap is permanently fixed

Archives kept fast-failing (~40 s) with *"Your account has reached the maximum
number of certificates."* Cause: cloud signing mints a **new Apple Development cert
per build machine**, and every CI run is a fresh throwaway cloud Mac, so they
accumulated to Apple's cap — previously requiring the owner to revoke by hand.
`testflight.yml` now has a **"Free up Apple Development certificate slots"** step
using the existing App Store Connect key. Distribution certs untouched;
`continue-on-error` so an API hiccup can't block a build. **No owner action ever
again.** Documented in `docs/testflight-ci.md`.

> **Dead end — do not retry:** forcing `CODE_SIGN_IDENTITY="Apple Distribution"` on
> the archive fails; the project uses automatic signing (*"conflicting provisioning
> settings … switch to manual signing"*, and SPM deps then demand a team).

## Testing gap — why these bugs shipped

Group Listen shipped with **zero tests**, and its sync logic lived inside methods
that call live services, so even the pure decisions weren't testable. The feature is
genuinely **device-only** (real radios, two accounts, audio) — unit tests can't
reach it. Response: every sync decision was extracted into **pure static functions**
and pinned in `GroupListenSyncTests` (epoch filter, intro-vs-stop resolution, drift
tiers + trim direction/scaling/bounds, join-code alphabet, wire-format round-trip
and backward compatibility), plus group-link cases in `DeepLinkParsingTests`. The
durable lesson: **for device-only features a real two-phone smoke test before "done"
is not optional** — #396 merged "additive and menu-gated" without one, which is how
the owner became the first tester.

## Scrub-bar jump — fixed after a mis-diagnosis worth recording ([PR #434](https://github.com/ehky2882/TRAVEL-GUIDED-TOUR/pull/434), squash `8bd32d3`)

Doing the owed solo-playback check, the owner found scrubbing "very slightly
strange" — narrowed (by offering candidate descriptions) to **the position
settling/jumping a moment after letting go**.

**First attempt was wrong.** Claude assumed the cause was AVPlayer's *tolerant*
default seek landing near, not at, the drop point, and switched the three
deliberate one-shot scrubs (player, tour detail, lock-screen slider) to the
precise zero-tolerance seek. That is a real improvement to where audio *lands*,
but it did not fix the visible jump — and **made it slightly worse**, because a
zero-tolerance seek takes longer to resolve.

**Actual cause:** `player.seek(...)` is **asynchronous**, but the periodic time
observer (0.5s) unconditionally overwrote `currentTime` with the player's
reported position. A tick landing *between* issuing the seek and its completion
reports the **pre-seek** position, clobbering what the scrubber just committed —
so the bar jumps back, then forward again when the seek lands. Longer seeks widen
that window, which is exactly why attempt one appeared to do nothing.

**Fix:** suppress the observer between issuing a seek and its completion
(`isSeekInFlight`), mirroring the existing `isAwaitingFirstPlayTransition` guard
that already covered the analogous *load* window. A `seekGeneration` counter means
only the newest seek's completion lifts suppression (fast repeated scrubs, or a
seek cancelled by loading a new item), and `play(url:)`/`stop()` invalidate any
in-flight seek so the flag can never stick. **Owner-verified on 1.1 (40).**

`skip(by:)` (±10/15s) deliberately stays **tolerant** — rapid taps would make an
exact seek per tap feel sluggish, and the small offset isn't noticeable there.

**Durable gotcha:** anywhere `currentTime` is published from both a synchronous
setter *and* a periodic observer, the async gap is a clobber risk. This codebase
now guards two such windows (load, seek); a third would need the same treatment.

**Process note:** the first fix shipped on a theory Claude could not verify
locally, and cost a build. When a device-only symptom resists one fix, get a
precise description (what moves, and when) before writing more code.
