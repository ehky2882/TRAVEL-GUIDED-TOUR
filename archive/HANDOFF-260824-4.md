## 1. The finding the whole thing rests on

All three platforms publish an embed that needs **no API key, no registration, no app review**.
Verified live 2026-08-24, not assumed:

| | Endpoint | Result |
|---|---|---|
| TikTok | `tiktok.com/player/v1/{id}` | **HTTP 200**, unauthenticated |
| YouTube | `youtube.com/embed/{id}` | standard iframe |
| Instagram | tokenless oEmbed | reachable — Meta reversed the token requirement 15 Jun 2026 |

**🔴 This is an EMBED, never a copy.** Bytes stream from the platform; we never fetch or re-serve
them. TikTok's API exposes **no video-file field at all** — not a permission that can be
requested — and their terms forbid getting one another way. **Only the thumbnail is re-hosted**,
because TikTok's thumbnail URLs are signed with `x-expires` and go blank within days.

⚠️ **An embed still cannot do what Atlas is for**: needs signal, needs the screen on, no offline,
no geofence audio, no Group Listen, no download. That is *why* `TourKind.link` exists rather
than link pins pretending to be tours.

## 2. 🔴 THE ORDERING HAZARD — read before publishing anything

**A link pin must NOT reach the live catalogue before a build that understands it.**

`TourKind` is a closed `Codable` enum, so an unknown `kind` **throws** — pinned by
`ToursDataDecodingTests.test_decodingTour_badKind_throws`. `ToursData` decodes the whole array
at once, so **one** `kind: "link"` fails the entire catalog decode, and `RemoteCatalogLoader`
then keeps the last good copy. **Every app build predating this change silently stops receiving
catalog updates.** No crash, no error, no sign anything is wrong.

**So: merge → TestFlight → install → only then publish a pin.**

⚠️ **Worth fixing before the App Store:** decode an unrecognised `kind` to a safe default rather
than throwing. A strict enum on a *remotely loaded* catalogue means every future kind breaks every
already-shipped version. Same argument for `triggerMode` and `primaryCategory`.

### 🔴 Three things made it far smaller than planned — each verified, not assumed

1. **`Stop` needed NO change.** All six `audioURL` readers already go through `URL(string:)`,
   which rejects `""` — so the empty-audio shape a fresh maker draft already writes carries a
   link pin safely.
2. **The geofence is safe by construction.** `ProximityMonitor` registers only `.geofenced`
   stops; a link pin's is `manual`.
3. **The map pin is free.** `MapMarkers` already draws any stop at `order == 0`.

### 🔴 A bug the tool's own self-test caught within a minute

The first domain check asked whether the host's labels *contained* `"tiktok"`, so
**`tiktok.evil.com` passed** — a hostile URL would have rendered a pin captioned *OPEN IN TIKTOK*
whose embed and whose tap both went elsewhere. **Both the Swift and the Python were wrong the same
way.** Now matched on the registrable domain only, pinned by
`test_platform_rejectsALookAlikeSubdomain`.

## 5. Decided but NOT built — the maker design

**Owner, 2026-08-24: *"these makers should be 'TikTok @asdfa;sldfkjds' or 'Instagram
@asldjfa;sdf'... so on so forth."*** The maker **is the creator**, so tapping through shows
everything pinned from them — a real feature, not just a credit line.

`make-link-pin.py` currently takes `--maker <uuid>` and emits **no maker row**. It needs to:

- mint a deterministic id — `uuid5(NAMESPACE_URL, "atlas-maker:tiktok:@handle")` — so the same
  creator always lands on the same maker
- emit a `makers` entry: `displayName` = `"TikTok @handle"`, `websiteURL` = the oEmbed
  `author_url`, `avatarInitials` + `avatarColor` (oEmbed carries **no avatar URL**)
- `userId: null` — nobody logs in as these, same as the Atlas studios

⚠️ **The fixture in §4 uses Atlas Studio NYC as a placeholder.** It does not affect whether the
embed renders. Do not read it as the intended design.

⚠️ **Consequence for the owner to weigh:** Settings → About counts makers as **"Dozents"**
(currently 41). Every pinned creator adds one, so people who never signed up would start counting
as Dozents. Raised, not yet answered.
