## 🔴 The finding worth keeping: a 429 that read as "no match"

The first geocoding pass hit Nominatim and came back with **30 "NO MATCH" out of 35** — including
**Tribune Tower**, which is unambiguously in OpenStreetMap. That implausibility is the only reason
it got a second look. The raw response was:

```
HTTP=429 Too many requests
```

The script had `except Exception: j=[]` around the JSON parse, so **every rate-limited fetch became
an empty result set, and an empty result set printed as "NO MATCH"** — a failed check returning a
clean-looking negative. This is `CLAUDE.md` § Reading a check's result, third row (*the checker
that fetched nothing*), reappearing in a script written this session rather than in one of the
checked-in tools.

**What made it survivable was not the error handling — it was reading the counts.** Had the batch
contained only obscure subjects, 30 plausible "no match" lines would have been accepted, and the
pins would have shipped without coordinates or, worse, with hand-recalled ones.

Rewritten to read `%{http_code}` explicitly and separate three outcomes — *fetched and found*,
*fetched and genuinely empty*, *did not fetch* — then re-run against Photon, which answered.
34 of 35 resolved; the 35th (Magazzino Italian Art) needed a location-biased query.

## Each pin minted individually, and why that matters

`make-link-pin.py:1107` reads `title=a.title if len(rows) == 1 else None` — **`--title` is ignored in
a `--batch` run**, and the title then falls back to the source caption truncated to 60 chars. On
TikTok that is usually tolerable. **On Instagram the caption is a paragraph**, so a batch run would
have named the first pin:

> *Architecture worth traveling for. 🤍☕🌿 Designed by @marlonbl…*

So the batch was minted as **35 separate single-URL runs** driven from a TSV, each with its own
`--title`, `--slug`, `--category` and `--tags`, outputs written to per-pin files and combined on
disk. The conversation never saw a pin's JSON.

⚠️ **This is a real limitation of the batch path for Instagram-heavy work**, not a preference. Worth
either teaching `--batch` a title column or noting it in the runbook.

## The Pages deploy, and why "pushed" is not "serving"

For roughly twelve minutes after the `gh-pages` push succeeded (`96e4906`, rebased onto another
session's `a59e9e3`), **every new hero URL returned 404**. That is the window `CLAUDE.md` warns
about, and it is long enough to look like a failed upload.

It was not. The Actions run list showed **`pages build and deployment` run 875 `in_progress`** on
exactly `96e4906` — and, one row below, **run 874 `cancelled`**, superseded by mine. Deploys on this
repo take ~9–10 minutes; the heroes went live at **~390 s** into the wait.

**Check the deploy run before concluding an upload failed** — a 404 during that window is the queue,
not a lost push. A *cancelled* run on your own SHA is the case that actually needs re-triggering.

Verified afterwards rather than assumed: **all 35 live URLs hash byte-identical to the uploaded
files**, and `check-image-duplicates.py --pins` returned **0 errors across 1,661 pin images** with a
fresh run stamp — the count itself being the evidence it fetched anything at all.
