## 🔴 The bug worth carrying forward

**Opening a saved tour hung the app until the watchdog killed it (`0x8BADF00D`). Four builds. Three diagnoses were wrong. The cause was an `if` inside `.toolbar`.**

The symbolicated build-84 log:

```
UISheetPresentationController._sheetLayoutInfoLayout:
  -> _UIHostingView.layoutSubviews
    -> ViewGraph.updateOutputs
      -> UIHostingController.preferencesDidChange
        -> ToolbarBridge.preferencesDidChange
          -> UIKitToolbarStrategy.updateLocations()
```

**No app frames in the stack at all** apart from `App.main()` at the bottom. The loop is entirely inside SwiftUI's toolbar bridge: the sheet lays out → SwiftUI renders → the toolbar's preferences change → updating the toolbar changes the **navigation bar's metrics** → changed metrics re-run the sheet layout that is still on the stack.

### Two durable rules

1. **Never wrap `ToolbarItem`s in a conditional, and never swap one item for another.** Declare each item unconditionally at a fixed placement; put all conditionality *inside* its content. Here `if outcome == nil { … }` wrapped both items, and a second `if` swapped the leading item between a `Text` button and an `Image` button. **The old `CreateTourView` had the same two placements and never hung — its toolbar had no `if` in it.**
2. **Nothing a sheet's own layout reads may change during the presentation transition.** The entire stack sits inside `_transitionWillBegin:`. Only the edit path trips it, because only `loadExistingTour` mutates state in that window — which is exactly why creating a tour was always fine, and why three wrong theories each looked plausible. The footer's hint line was a second such input (a `.safeAreaInset` whose height changed the moment a saved tour finished loading); it now reserves two lines regardless of content.

### How three builds were lost

**I worked from the build-77 log for three builds and never asked for a fresh one**, so each fix was aimed at a snapshot that predated the previous fix. That log was also **unsymbolicated for the app frames**, and I read its `NavigationStack.init(root:)` frame as *the body being evaluated* when it was **the toolbar's host**. From there I reasoned about raw `imageOffset` values and even decoded the instruction bytes at the program counter — all inference, all wrong. The build-84 log arrived symbolicated and named the function outright.

**When a fix fails, get the log for the build that failed.** Do not re-reason over the old one.

`.ips` files live on the phone at **Settings → Privacy & Security → Analytics & Improvements → Analytics Data**; the filename's trailing digits are `HHMMSS` local. A `.cpu_resource-*.ips` beside it is a **sampled profile** and is often more useful than the crash log when the symptom is a spin.

### Dead ends — shipped, wrong, and deliberately kept anyway

- **`DismissAttemptGuard`** (build 81) — a `UIViewControllerRepresentable` setting `isModalInPresentation` to prompt on the swipe. Deleted; it was mutating sheet state from inside sheet layout, which is a real hazard, just not this one.
- **The camera-write guard and the cheap dismiss guard** (build 84). **Both kept.** `CLLocationCoordinate2D` has no `Equatable`, so an unchanged write still dirties the view, and `.interactiveDismissDisabled` reconfigures the presentation controller — so neither is wrong. They just weren't the bug.
- **Clamping the loaded radius** — a real latent bug (tours predate the 15–100 slider), also kept, also not this.

## Process notes

- A CI build log carried **exactly one `error:` line in 95,219 characters** — grep the whole log, never tail it.
- **`Self` is rejected in a stored-property initializer** even on a `final class` ("covariant 'Self' type cannot be referenced from a stored property initializer") — use the type's own name.
- The **job-status API lags**: a job reporting `in_progress` had already written `** TEST SUCCEEDED **` to its log.
- A CI unit-test job hung past 20 minutes with no downloadable logs; the documented **cancel-and-rerun** cleared it and the same job then finished in 3 minutes.
- **Build numbers are `github.run_number` and shared across every session** — this build was dispatched expecting 82 and came back **84**. Read the number back after dispatching; never promise it in advance.
