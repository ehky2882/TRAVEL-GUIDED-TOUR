# HANDOFF 2026-09-03 (session 141) — the bottom module goes missing: it was hidden, not uninstalled

**Branch:** `claude/bottom-module-missing-45z6ep` · **PR:** [#728](https://github.com/ehky2882/TRAVEL-GUIDED-TOUR/pull/728) · code only, no SQL, no catalogue change.

## The report

A tester sent a screenshot: no mini-player, no tab bar. Home tab, drawer at half
detent, map settled, "Continue listening" populated, real location in Porto. The
drawer's bottom edge sits ~126pt above the screen bottom with **map showing
through** — space reserved, nothing painted.

## What the screenshot ruled out, before any code was read

The launch entrance drives the search bar in from the right and the drawer up
from below off the same `handOffProgress` the module reads. Both are **settled**
in the frame. So `handOffProgress` reached 1 and the launch completed — which
kills the obvious first theory (module stuck at `assemblyProgress == 0`, i.e.
offset off-screen at opacity 0). Worth doing that check first on any future
report: **the other two edges of the assembly are a free witness for the third.**

`ContentView.swift:564` passes `bottomReservedHeight: AtlasBottomModule.height()`
**unconditionally** — it never reads `hidesBottomModule` — which is why the space
is reserved whether or not the bars exist. That is what makes the screenshot
diagnostic rather than ambiguous.

## The cause

🔴 **Three previous fixes all asked whether the secondary window INSTALLED. This
is a different failure: it installs fine and is then left HIDDEN.**

The launch hides it deliberately — the window sits at `.normal + 1`, above every
window in the scene, so it would paint over the splash. But the hide was
**latched** off `launchState.isSplashVisible`, against a single matching unhide
buried in `runLaunchGate`:

```swift
bottomModuleWindow.setHidden(false)             // phase is STILL .splash
try? await Task.sleep(for: .milliseconds(32))   // guaranteed suspension
await playHandOff()                             // beginHandOff() at last
```

`isSplashVisible` is `phase == .splash`, and `phase` doesn't move until
`beginHandOff()` — **32 ms after the unhide, with the main actor yielded**. Any
`installBottomModule()` landing in that gap hits:

```swift
if launchState.isSplashVisible { bottomModuleWindow.setHidden(true) }
```

and re-hides the window **with nothing left to undo it**. `scenePhase == .active`
calls `installBottomModule()` **unguarded**, and on a cold launch that transition
lands right around there. On a busy launch (catalog decode, map tiles, image
warmup) the main-actor hop makes the window wider than 32 ms.

Result: bars gone for the entire session, on every tab, no way back but a
force-quit.

**And `ContentView`'s inline fallback (#443) could not catch it** — it asked
`!isInstalled`, and the window *was* installed. So neither surface drew the bars.
That is the whole reason the fallback didn't cure a symptom it was written for.

## The fix (PR #728)

Structural, not another timing bet.

1. **The App owns `launchHoldsBottomModule`**, dropped in the **same main-actor
   turn** as the unhide, and `installBottomModule()` **re-derives** visibility via
   `BottomModuleWindowController.shouldWithdraw(launchHoldsModule:withdrawnByScreen:)`
   instead of commanding a hide. A duplicated or mistimed call can only reach the
   right answer — and since that site runs on **every foreground**, a
   background round-trip becomes a guaranteed recovery.
2. **The fallback asks `isShowingBars`** (`isInstalled && !isHiddenByRequest`),
   via `rendersInlineFallback(isShowingBars:withdrawnByScreen:isSplashVisible:)`.
   An installed-but-hidden window is now covered; worst case is bars below a
   UIKit modal rather than no bars.
3. **`setHidden` writes the window every call** instead of early-returning on an
   unchanged flag, so a drifted window state self-corrects. The *flag* is still
   only written on a real change, so re-asserting doesn't churn observers.

7 new tests (15 total in `BottomModuleWindowTests`). The regression one pins that
re-deriving after the unhide says **show** at the exact instant the old code
still said hide.

## Deliberate non-fixes and risks, stated not buried

- ⚠️ **If `appShared.hidesBottomModule` were itself stuck true** (a missed restore
  from a link pin's element fullscreen), this re-derives *from* the stuck flag and
  cannot heal it. `LinkEmbedView` guards it with three restore paths —
  `dismantleUIView`, `Coordinator.deinit` (the only ARC-guaranteed one) and
  `TourDetailView.onDisappear` — so it was left alone rather than adding a rule
  that could fight the tour wizard, which legitimately withdraws the module from
  a `fullScreenCover` over the Me tab root.
- ⚠️ **`ContentView.body` now depends on the launch PHASE** (changes twice a
  launch), **not** on `handOffProgress` (60 Hz, still read only in leaves — the
  session-102 fix is intact). The splash guard exists so the window's copy and the
  inline copy never co-render, which would put **two `fullScreenCover`s on one
  `showingFullPlayer`**.
- ⚠️ **Nothing compiled locally** — Linux web session, no Swift toolchain. CI is
  the check.

## Owed

**Device verification, and it is the real proof.** The bug is intermittent by
nature, so the honest check is repeated cold launches (force-quit, relaunch) plus
a background→foreground round-trip. New behaviour worth confirming: if the bars
ever do go, **backgrounding and returning should now bring them back** rather
than needing a force-quit.
