## 🔴 Both branches were ORPHAN COMMITS and could not be merged at all

The reason the previous session's work never reached the PR queue was not only its
missing GitHub API access. **`c17831f0` had no parent** — a root commit carrying the
entire tree as "added" — so GitHub refused the PR outright:

```
The claude/catalog-forward-compat branch has no history in common with main
```

`5c1db5df` was stacked on it and inherited the problem.

**⚠️ `git merge-base` piped through `xargs` LIES ABOUT THIS.** With no common ancestor
it prints nothing and exits 1, so `git merge-base A B | xargs git log --oneline -1`
runs `git log` **bare** and prints HEAD — which reads exactly like a clean merge base.
That produced a confident, wrong "no conflicts" report in this session before the
GitHub error exposed it. **Check the exit code, or use `git merge-base --is-ancestor`.**

**The fix preserves the trees byte-for-byte.** `git commit-tree <tree> -p <real parent>`
re-parents without re-authoring; `git diff` between old and new commit is empty. A full
diff against `main` then showed exactly the 17 intended files, no strays, no deletions
— which is also what proved the orphan's "162,897 additions" was an artefact of having
no parent to diff against, not a runaway commit.

Every live `kind` (`single`, `multiStop`), `triggerMode` (`geofenced`, `manual`) and all

**⚠️ A first attempt at this reported 9,540 failures and was MY OWN BUG** — the regex
swept up **computed** properties (`coordinate`, `isPaid`, `primaryTag`, `storeProductId`,
`fallbackPriceText`) as though they were decoded fields. When simulating a decoder from
source, exclude anything whose declaration is followed by `{`. A scary number from a
hand-rolled check is a reason to re-read the check first.

## 🔴 A live ordering hazard nobody had named

**`claude/project-tracking-dashboard-1kggmu` (unmerged, no PR) carries
`backend/restore_catalog_keys.sql`, which does `create or replace function
public.get_catalog_core()` with a full inline body.**

`split_link_pins.sql` renames `get_catalog_core` aside to `get_catalog_core_base` and
wraps it. **Running `restore_catalog_keys.sql` now would overwrite that wrapper, sever
the split, put link pins back inside `tours` and silently re-freeze every old build.**
It is the fifth file in this repo with the inline-`get_catalog` shape that § "create or
replace get_catalog() NOW DESTROYS THE PLACE LAYER" documents for the other four.

`scripts/check-catalog-keys.py` catches it after the fact (it fails when `linkPins`
vanishes), but ordering is the cheaper defence. **Either give that file the warning
banner the other four carry, or delete it, next time that branch is touched.**

## Process notes

- **`ci.yml` fires only on `pull_request: branches: [main]`.** A stacked PR whose base is
  another branch gets **no automatic CI** — dispatch `workflow_dispatch` manually. Once
  the parent merges, GitHub retargets the child to `main` and normal triggering resumes.
- **A squash merge leaves the child PR showing the parent's diff too** (25 files here,
  not 12), because the parent's commits are not ancestors of `main`. Re-parent the child
  onto merged `main` before review — the tree is unchanged, only the base moves.
- `git fetch` (no args) times out against the proxy; **`git fetch origin main` works**.
- The shell cannot reach `api.github.com`; poll Actions through the MCP tools. And
  `actions_list` on `publish-catalog.yml` returned **102 KB** and blew the tool budget —
  filter by branch, or read the saved result file.
- Both PR bodies were rewritten immediately before merging, since **the squash commit
  inherits the PR body**; #598's still said "Merge #597 first".
