## What's in the SQL

- **`tours.price_tier`** — int cents, **NULL = free**. CHECK-constrained to the 10 Phase-1 tiers (99, 199, 299, 399, 499, 699, 899, 999, 1499, 1999). The ASC product id is derivable: `tour.tier.` + zero-padded cents.
- **`purchases`** — one row per Apple sale = the buyer's entitlement **and** the maker's ledger entry. `apple_transaction_id` **UNIQUE** (StoreKit-history replay after a dead spot is a no-op). Stores the tier actually paid, so later price changes don't rewrite history. `apple_environment` keeps Sandbox rows out of earnings. `user_id` is `on delete set null` and `tour_id`/`maker_id` are `on delete restrict` — a sold tour can be taken down but never hard-deleted, and account deletion never destroys a maker's earnings history.
- **`payouts`** + `purchases.payout_id` — Phase 5 stamps rows as paid.
- **`maker_payout_accounts`** — the Stripe Connect account id. **Read-only to clients.**
- **`maker_net_cents(tier)`** — `0.85 × 0.80` = 68% of sticker (Apple 15% Small Business → Atlas 20% of the remainder). Single place to change if a rate moves.
- **`maker_sales`** view — a maker's own sales **without `user_id`**, self-scoped via `owns_maker()`/`is_admin()`.
- **`maker_earnings`** view — units, gross, earned, accrued-unpaid, paid-out, refunded-after-payout. Production + non-refunded for the sales counters; `paid_out_cents` comes from `payouts.amount_cents`. Phase 4's Earnings screen reads this.
- **`get_catalog()`** — full rebuild, identical except a new `'priceTier'` key. Old app builds ignore it. (`paid_tours.sql` also `add column if not exists video_urls` first, because a `language sql` body is parsed at CREATE time and would abort the whole transaction on a project where `add_video_urls.sql` was never applied.)

**RLS:** `purchases` has **no client writes at all** and is readable only by the **buyer** (+ admin) — makers deliberately have no policy there, so they can't enumerate who bought what; they read `maker_sales`/`maker_earnings` instead. `payouts` read = paid maker + admin, write = admin. `maker_payout_accounts` = read-only to the owning maker + admin.

## Three deliberate deviations from the design doc (don't "fix" them)

1. **`maker_payout_accounts` table, not `makers.stripe_account_id`.** `makers` carries a **public-read** RLS policy (`makers_public_read ... using (true)`), so a Stripe account id column there would be readable by every anonymous client. It's also **not client-writable**: `stripe_account_id` decides where money lands, and `accounts.sql` auto-creates a maker row for every signup, so a writable policy would let any session redirect payouts. Real write path = Stripe Express onboarding callback via the service role (Phase 5).
2. **Neither Edge Function trusts its caller's payload.** Both extract *only* a transaction id from the incoming JWS, then fetch the authoritative record from **Apple's App Store Server API** (production host, falling back to sandbox) under our signed ES256 JWT, and act on that. So a forged POST can neither mint an entitlement nor fake a refund. The unverified local decode is used for id extraction only — never as a recorded fact. This is why the App Store Connect **In-App Purchase API key** is required.
3. **Makers never see buyer identities** — the earnings ledger was not meant to double as a customer list.

## ⚠️ Hardening pass (same session, after an adversarial review) — PR #433

The first PR (#431) merged, then a skeptical re-review found a **critical hole**. Nothing had been deployed (the owner hadn't run step 1), so there was **no live exposure** — but it would have shipped money-losing behavior:

**The critical one: `record-purchase` never compared the tier bought against the tour's price.** The tier products are reusable across every paid tour, so Apple's receipt proves *"someone paid $0.99"* but never *which tour*. An attacker could buy the cheapest paid tour, then re-POST that **genuine** receipt with a $19.99 tour's `tourId` — every check passed (Apple confirms it, bundle matches, product is a tier, not revoked) and they'd get a full entitlement while that maker was credited 99¢, permanently, in the ledger the design doc calls financial data. **Apple cannot catch this; only we can.** Now: the tour's `price_tier` must equal the tier paid, and free tours are rejected. **If you touch that function, keep that comparison.**

**A second money bug, caught by a verification pass over the fix itself:** `appstore-notifications` returned **200 on an Apple-side failure**. This endpoint's only retry mechanism is Apple's own, and Apple retries on non-200 — so a 200 during an Apple outage meant Apple gave up and a **real refund was dropped permanently**, leaving the sale counted and the maker overpaid. It now returns **500** on `unavailable` so Apple retries; a genuine not-found still 200s (nothing to do).

Also fixed in the same pass:
- **Buyer identity is verified, not decoded.** Was `unsafeDecodePayload(jwt).sub`, safe only while the dashboard's "Verify JWT" toggle is ON — and its sibling function ships with instructions to turn that toggle **OFF**. One misclick and `user_id` becomes attacker-chosen. Now a real `GET /auth/v1/user` call to GoTrue.
- **Apple outages no longer read as "your purchase doesn't exist."** `fetchTransaction` now distinguishes `not_found` (both hosts 404) from `unavailable` (5xx / 401-bad-credentials / unreachable) → **503, retry** instead of a permanent-looking 422.
- **`maker_earnings.paid_out_cents` reads `payouts.amount_cents`** instead of re-running `maker_net_cents()` over old sales. Otherwise dropping the platform fee would instantly re-value every historical payout and disagree with the bank. New `refunded_after_payout_cents` makes a post-payout refund visible instead of silently vanishing (there's still no clawback row type — Phase 5 decision).
- **`tourId` is UUID-validated and escaped** before entering a service-role PostgREST query (was raw interpolation — an `&` could smuggle extra query params).
- **`purchases.price_tier` gained the same CHECK** as `tours.price_tier` (the regex accepted `tour.tier.0000` → 0).
- **A transaction already redeemed by a different buyer returns 409**, not a false `{ok:true}` (with `ignore-duplicates` + `return=minimal` the insert can't tell you it was someone else's).
- **Zero-match refunds are logged** (`Prefer: count=exact`) — Apple can notify before the app records the purchase, and PostgREST returns 204 either way.
- **`payouts` admin-write policy got its missing grant** (a policy without a grant is inert under PostgREST).
- **`.p8` secrets with literal `\n` are normalized**, with a clear error instead of an opaque throw on every purchase.
- **Explicit `revoke` on `maker_payout_accounts` and `purchases` writes.** Grants are cumulative — *deleting* a grant statement from the file doesn't take the privilege back on a database where the earlier revision already ran. RLS blocked the writes anyway, but the file now says what it means.
- **Apple `400` (malformed transaction id) is terminal, not transient.** The id is client-supplied, so classifying 400 as "unavailable" handed a caller an endless 503 retry loop. 400 and 404 now both mean "not here"; only 401/403/429/5xx/unreachable are retryable.
- **The tour lookup filters `status=eq.published`.** It's a service-role read, so without it a draft or taken-down tour with a price was purchasable by anyone who knew its UUID.
- **`security_barrier = true` on both views** so the planner can't push a cheap user-supplied qual ahead of the `owns_maker()` check.

Verified: SQL structurally re-checked; both functions `tsc --noEmit` clean (only Deno/`npm:jose` globals unresolved, expected). A verification agent re-read all three files against the claimed fixes and confirmed the tier binding, GoTrue gating, 409-not-on-same-user-replay, `full outer join ... using` validity, definer-view scoping, and idempotency (including that `create or replace view` only appends columns — the new `refunded_after_payout_cents` is appended last, so it replaces cleanly).

## Notes / gotchas

- **`price_tier` must never enter `seed_from_toursjson.py`.** Price is maker-set in the DB, not in `Tours.json`; the seeder's tour upsert omits it from the column list *and* the `DO UPDATE`, so a content re-seed preserves prices and new tours default to free. A comment in the file says so — verified by regenerating the seed (914 tours, 0 occurrences of `price_tier`).
- **No Postgres in this session**, so the SQL wasn't executed — only structurally checked (balanced parens/dollar-quotes; the odd single-quote counts are all apostrophes inside comments). First real execution is the owner's step 1; if anything errors, fix and re-run — the file is idempotent.
- **Pricing a tour before Phase 4's maker UI:** `update public.tours set price_tier = 299 where id = '<uuid>';` — `null` puts it back to free.
- Sandbox purchases record with `apple_environment = 'Sandbox'` and are excluded from `maker_earnings`, so Phase 3/6 testing can't pollute real earnings.
- Widening the tier menu later = create the ASC product first, then extend the CHECK constraint in `paid_tours.sql` (it's the only place the list is enforced; the functions accept any `tour.tier.<digits>` product Apple confirms).
