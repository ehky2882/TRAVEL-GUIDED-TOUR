## 1 — the crop

**🔴 THE CAUSE: A REEL WAS BEING SIZED BY THE PHOTO CAROUSEL'S SQUARE.**
`TourDetailView.instagramPlayer` passed `GalleryVideoView` a `height` of nil. That means "take
`AtlasSpacing.heroAspectRatio`" — and **that constant is `1.0`**. `VideoSurface` then fills its box
with `.resizeAspectFill`, so a **720×1280** reel was cropped to a square: the **middle 56% of every
frame**, with the creator's own titles cut off top and bottom. On the test pin both lines of
*"NYC's Forgotten Names & Places Volume 35"* / *"Division Street: Delancey vs Rutgers"* were sliced.

**⚠️ The `.aspectRatio(9/16, .fit)` the caller already wrapped the box in did NOT save it.** The
child imposes its own square, and the square wins. Reading the call site alone suggests the shape
was already handled; it was not.

**⚠️ THE FILL IS A DELIBERATE OWNER DECISION AND IT STAYS — FOR THE CAROUSEL.** `VideoSurface`
carries a 🔴 comment explaining it: there a clip is one page among photographs that are fill-cropped
into the same square, and the expand button is what shows the whole frame. **That reasoning is
about a clip sitting BESIDE PHOTOGRAPHS, and it does not survive the trip to a link pin, where the
post is the entire page and there are no photographs beside it.** So the fix is an **opt-in**, not a
change of default:

- `GalleryVideoView.fittedAspectRatio: CGFloat?` — nil keeps the hero square and the fill.
- Non-nil sizes the box to that ratio and switches the surface to `.resizeAspect`.
- `TourMediaCarousel` does not pass it, so the ordinary gallery is byte-for-byte unchanged —
  **re-checked on Shinsegae Media Facade after the change: still square, still filled.**

**⚠️ `VideoBoxSizing` is a `ViewModifier`, not an `if` around the content, and that is deliberate.**
A branch would give the two shapes different view identities and SwiftUI would tear down and rebuild
the `AVPlayerViewController` — and with it the player — whenever it changed.

**⚠️ The ratio is passed in rather than measured.** `LinkSource.embedAspectRatio(for:)` knows the
shape from the URL before a byte is fetched, so the box is right on the first frame; adopting the
asset's measured ratio later would resize the page under the reader's thumb. It is also **the same
expression the embed branch uses**, so the page cannot change size depending on whether a resolve
succeeded — and it is the shape a TikTok pin already gets, which is the whole point of the resolver.

**✅ The 9:16 box adds no letterboxing of its own — measured, not assumed.** Six live pins
(Division Street, Wave Hill, Park Side Donuts, IAC Building, Blenheim Palace, Museum of Ethnography)
read with AVFoundation are **all exactly 720×1280 → 0.562**. Black bands some reels show are baked
into the source by the creator; no crop removes them without taking picture with them.

## 2 — the scrubber

**🔴 THE CAUSE: THERE WAS NO CLOCK.** `scrubPosition` read `player?.currentTime().seconds` — a plain
`AVPlayer` call with nothing observable about it — so **SwiftUI had no reason to re-render**. On a
1m 49s reel the elapsed label sat at `0s` and the brass fill stayed empty for the whole clip, which
is exactly what "the scrubber doesn't work" looks like.

**⚠️ ONLY GALLERY CLIPS EVER SHOWED IT, and that is why it survived this long.** A `.narration` clip
is slaved to `AudioPlayerService`, which **is** `@Observable`, and the view already re-renders on
`.onChange(of: audioPlayer?.currentTime)` every tick. **Every link pin is a gallery clip.**

The fix is a periodic time observer at **0.25 s** writing into `@State playbackTime`, delivered on
the main queue (the same contract `collapse()`'s `asyncAfter` already relies on).

- **⚠️ Installed BEFORE `player` is published**, so a sample cannot land on a view that has not
  adopted the player yet.
- **⚠️ Removed in `onDisappear`** — an observer left on a player that outlives the view retains the
  closure and keeps firing.
- **⚠️ `playbackTime` is seeded from `request.startSeconds`**, so expanding mid-clip starts the bar
  where the picture already is rather than at zero.
- **⚠️ `seek(to:)` writes the position through immediately** on the gallery branch. The observer
  fires up to a quarter-second later, and until it did the bar would spring back to where the finger
  started.

## The cause, which is two faults stacked

1. **`og:image` was hardcoded** in `site/t/index.html` (and `/m/`, `/p/`, `/l/`) to
   `ehky2882.github.io/…/images/atlas-icon.png` — **the pre-#353 green-sphere
   placeholder**. The brass icon shipped in the app and *this copy was never
   updated*, so a placeholder outlived the thing it stood in for by four months.
2. **🔴 THE ONE THAT MATTERS: the per-tour title and description were patched from
   JavaScript, in `render()`, after the catalog fetch resolved. LINK-PREVIEW
   CRAWLERS DO NOT RUN JAVASCRIPT.** They read the bytes the server sends and
   stop. So every shared link previewed identically whatever it pointed at — and
   **nothing in that script touched `og:image` at all**, so a tour hero could never
   have appeared however the JS ran.

Fixing (1) alone would have shipped a correct-looking icon and still no tour photo.

## The fix

`site/api/share.js` — one Vercel Node function serving `/t/`, `/m/`, `/p/`, `/l/`.
Reads one row from Supabase with the **publishable key** (client-safe, RLS-gated,
already ships in the app) and bakes real tags into the response.

- **⚠️ THE STATIC PAGES ARE DELETED, AND THAT IS LOAD-BEARING: VERCEL CHECKS THE
  FILESYSTEM BEFORE `rewrites`.** Leaving `site/t/index.html` in place means it
  silently wins and the function is never reached. Do not restore them.
- `/g/` stays static — a join code has no subject to look up — and only lost the
  green icon.
- The card is server-rendered too. **The old page downloaded the whole ~7 MB
  `Tours.json` in the browser to display one tour.**
- Query shapes, all anon-readable and verified live:
  `tours?id=eq.<uuid>&select=…,makers(display_name)` (one call, embed works) ·
  `places?id=eq.<uuid>` · `makers?id=eq.<uuid>` · `rpc/get_journey` with
  **`{"p_journey": "<uuid>"}"`** (note the param name — `p_journey_id` 404s).
- ⚠️ **`tours` has `total_duration_seconds`, not `duration_seconds`.**
- Link pins are ordinary `tours` rows with `kind='link'`, so they share through the
  same path; the eyebrow reads **"Pinned post"**, because calling somebody else's
  post an "Audio tour" misdescribes it and Dozent hosts none of that media.

## Measured platform gaps — recorded in the function header, not papered over

Heroes are linked at their real URL, so two quirks follow. **Both were measured per
user-agent, not assumed:**
