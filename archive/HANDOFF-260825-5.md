## 3. 🔴 A list has an order somebody made by hand, so the sort needed a fifth state

The maker feed and a place have only *rules* to order by. A list has an **arrangement** — and Liked has `savedEntries`' newest-saved order, which cannot be rearranged at all. A sort offering only the four criteria would have been a quiet way to lose a curation.

So the stored criterion is **`AtlasTourSort?`**, and **nil means the collection's own order**. It is where the page opens (`@AppStorage` gives an optional RawRepresentable no default, which is exactly right here) and the menu always offers it back — labelled **"As arranged"**, or **"Recently saved"** on Liked.

`AtlasSortMenu` gained a second initialiser taking `Binding<AtlasTourSort?>` plus a `naturalLabel`. **The maker page's non-optional initialiser is unchanged and bridges through a computed Binding whose setter ignores nil** — with no `naturalLabel` the natural row is never rendered, so nil can never arrive there.

---

## 4. 🔴 Edit mode forces the arranged order AND the row layout

`effectiveLayout` / `effectiveSort` return `.list` / `nil` while `isEditing`, whatever the reader last chose.

**Why:** you can only rearrange what you can see *in the order you are rearranging*. Reorder arrows against an A–Z list would move rows in an order that is not on screen; a photo grid has nowhere to put them at all. Both are **computed rather than written back**, so leaving edit mode restores the reader's choice with no bookkeeping.

The two controls are **hidden** while editing, not disabled — a control that visibly does nothing is worse than one that is absent.

## 5. ⚠️ The cost of the grid here, stated rather than buried

**A tile has nowhere to put the curator's note** — the one thing a list row carries that no other tour row in the app does. That is why rows stay the default, and it is the one thing to watch if the grid ever becomes the default here.

## 6. Smaller things

- **`AtlasTourSort.sorted` gained a generic overload** taking a `tour: (Element) -> Tour` projection, so a caller holding `(item, tour)` pairs gets the same comparator and the same stability. The `[Tour]` version now calls it with identity. Tested: the note travels with its tour, and tied dates leave the arrangement untouched.
- **`LocationManager` is read optionally** here, as `libraryStore` and `authService` already are — not every layer that can reach a list injects everything. With no manager or no fix, the distance sort leaves the order exactly as it came (`AtlasTourSort.sorted` returns nil for every pair).
