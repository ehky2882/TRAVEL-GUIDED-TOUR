# HANDOFF — 2026-08-30 (session 126, local Mac — code)

## The ask

Owner:

> *"when i'm in a places page, or tour details page, or dozent page etc. in the 'map' view i want
> to be able to click on a button that 'expands' the map which effectively takes me back to the
> home map view at the location of that particular item. it will bring you to that view with the
> placecard showing, similar to if i were to get to a tour by searching."*

So: every inline map in the app is a **preview** — you can pan it, but you cannot browse on from it,
because it only ever holds that page's own pins. This is the door back to the one map that holds
everything, framed on whatever you were reading about.

**Built, compiled, `test_sim` 578/578, and driven end to end in the simulator on all three
reachable surfaces.** Branch `claude/map-expand-control`.

---

## What shipped

| Surface | Lands on | Card |
|---|---|---|
| Tour detail | that tour's pin, neighbourhood zoom | the tour's card |
| Place page | the site, neighbourhood zoom | **the place's own card** |
| Creator page (`TourSetMap`) | every tour that creator has, framed | none |
| List page (`TourSetMap`) | every tour in the list, framed | none |

Both owner decisions were taken at the top of the session, before any code:

- **Creator / list pages get no card.** They hold many tours across many cities and have no single
  subject; raising one tour's card would single it out arbitrarily. What you get is the picture
  their own `SHOW ALL` gives, on the map you can actually browse from.
- **A place raises its own card, not a member tour's.** A site with two or more published tours
  draws as ONE capsule pin on the home map, so a member's card would hang over a pin that stands
  for the place.

## The mechanism, and why it is small

**Search already did this.** `PendingMapMove` (`HomeSharedState.swift`) has carried a region plus a
`placecardTourId` since session 102, and `HomeView.flyTo` already raises the card *after* the
flight. So arriving from an expand button is byte-for-byte the same landing as arriving from a
search result — deliberately, because the one map should not look different depending on which door
you came through.

Three additions:

1. **`PendingMapMove.placecardPlaceId`** — the place flavour. `flyTo` prefers it over the tour id
   when both are set: a caller that knows a place id knows the more specific thing about where you
   are landing.
2. **`Features/Home/MapExpander.swift`** — the channel. `expand(to:showingTour:showingPlace:)` for a
   single subject, `expand(framing:)` for a set, plus the pure static `regionFraming(_:)`.
3. **`Components/MapExpandButton.swift`** — the control and a `.atlasMapExpandControl(isVisible:)`
   modifier, used by all four surfaces.

### 🔴 The two traps this had to avoid

**(1) Setting state is not enough — `performExpand` exists for the same reason
`TourPresenter.performDismiss` does.** Every surface with an expand button sits inside a UIKit
slide-up layer that completely covers the main window, and SwiftUI can stop delivering updates to a
covered hierarchy. An `.onChange` in `ContentView` may simply never run — that is the dead tab bar
of session 74, the dead place pin of #532, and the dead X of #535. So `ContentView` wires a closure
that tears the layers down **directly**:

```swift
mapExpander.performExpand = { move in
    tourPresenter.dismiss()      // each is idempotent — dismiss() no-ops
    makerPresenter.dismiss()     // when nothing is presented, so calling all
    placePresenter.dismiss()     // four is free and works from a page reached
    listPresenter.dismiss()      // through any stack of them
    appShared.selectedTab = .home
    DispatchQueue.main.async { homeSharedState.pendingMapMove = move }
}
```

**(2) The move is delivered on the next main-queue turn, deliberately.** Written synchronously it
lands while the main window is still covered and `HomeView`'s observer may never see it — a fly-to
that simply doesn't happen. `DispatchQueue.main.async`, **not** `Task { @MainActor in }`: main-queue
blocks run strictly FIFO, so it cannot overtake the dismissals above (the session-113 rule).

And **`HomeView` consumes the move from three triggers, not one** — first appearance, the request
landing, and **`isActive` becoming true**. That third one is not belt-and-braces: it is the reliable
signal on the path where Home was not the showing tab. `consumePendingMapMove()` clears the request,
so at most one of the three ever acts on it.

## Decisions worth not re-litigating

- **One component for all four surfaces.** This app has paid three times for a map idiom copied per
  surface — `StopPin`/`ClusterPin` drifted to 14pt against 16pt before `MapPins` was extracted, and
  the swallowed-tap placecard stack was two copies before `TourSetMap` was. A fifth map surface
  should call `.atlasMapExpandControl`, not grow a fifth copy.
- **Bottom-trailing**, matching the Home map's own control stack — and because the placecards these
  maps raise travel *upwards* from a pin sitting low in the frame, so a top-trailing button would
  sit where the top card lands.
- **Hidden, never disabled or inert**, when there is nothing to expand to (a tour with no stops, a
  creator with nothing published, a host that wired no layers). A control that visibly does nothing
  is worse than one that is absent; an *inert* one is the invisible-defect class this codebase keeps
  rediscovering.
- **The expand region is NOT the region the inline map frames**, and the two are legitimately
  different. Tour detail's preview frames the whole route so you can see the shape of a walk; the
  place page's is ~400 m of street. The Home map is for browsing on from, so both arrive at
  `HomeView.region(framing:)` — the same zoom Search uses.
- **`MapExpander.regionFraming` takes the PIN coordinate** — a single tour's only stop, or **stop 0**
  of a walk — not every stop and not the centroid. A walk's centroid can sit hundreds of metres from
  any of its stops (Montreal's Downtown walk: 197 m), which is the session-102 drawer bug.
- **`@Environment(MapExpander.self)` is optional at every call site** so previews still render; nil
  hides the button. That is a *visible* failure (a missing control), unlike the dead-control class,
  which is why it is hidden rather than assert-and-crash.

## Verification

- `build_sim` **SUCCEEDED**, no new warnings.
- `test_sim` **578/578** (was 570; **+8** in `MapExpandTests`): set framing uses pin coordinates not
  centroids, every pin lands inside the frame, nothing-to-frame reports nil, one tour is not
  zero-span, place and tour ids are carried separately, two expands to the same region are distinct
  events (`.onChange` compares on the id), an unwired expander is inert, a wired one delivers.
- **Driven in the simulator, all three reachable surfaces:**
  - **Tour detail** — Grand Army Plaza → Map → expand → Home map at the plaza, its card up
    (*"GRAND ARMY PLAZA, BROOKLYN / by Atlas Studio NYC / 1 mi away"*), drawer retracted.
  - **Place** (`dozent://place/73f7a252-…` Rijksmuseum) → Map → expand → Home map in Amsterdam with
    the **place** card up (*"RIJKSMUSEUM / 2 tours available"*).
  - **Creator** (`dozent://maker/946d6338-…` Atlas Studio AMS) → Map → expand → Home map framed on
    Amsterdam, **no card**, drawer collapsed.
- **List page not driven** — it is login-gated, and it renders through the same `TourSetMap` the
  creator page proved.

⚠️ **A harness artifact, not a product bug, recorded so the next session doesn't chase it.** On the
first creator-page attempt the tap "landed on the Me tab": the expand button's accessibility frame
sat at y≈808 on an 852pt screen, *underneath* the bottom-module window, so the synthetic tap went to
the tab bar above it. Scrolling the map fully into view first made it work. A real user scrolls
before tapping; but it is worth knowing that anything a page draws at the height of that bar is
unreachable — the same class as the `UIPageControl` trap in #571.
