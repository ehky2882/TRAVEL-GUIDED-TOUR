## 1. The `…` was gold because it named no colour

`TourListDetailView`'s chrome row drew back and bookmark through the shared
`chromeCapsule` and its overflow label as a bare
`Image(systemName: "ellipsis.circle")`. Two consequences, both in the owner's
screenshot:

- `ellipsis.circle` carries **its own drawn ring**, so it sat in no 44×44
  capsule and had none of the translucent fill its neighbours have.
- It stated no `foregroundStyle`, so it resolved the **environment accent** and
  painted brass beside two neutral capsules.

**This is the session-99 wordmark bug in a second place.** There, a call site
said `mapPin` and drew white because an ancestor `.tint` repainted it; here a
call site said nothing at all and took the accent. **The generalised rule: when
a control's colour surprises you, first ask whether the call site names one.**

Worth recording that the row's *existing* doc comment already claimed "the same
capsules, in the same places, as tour detail and the place page" — the comment
was right about the intent and the code had drifted from it. A comment asserting
consistency is not evidence of consistency.

**Owner direction: tour detail is the canonical example for now.** Verified by
diffing rather than by eye — `chromeCapsule` is byte-for-byte identical in
`TourDetailView`, `PlaceView` and `TourListDetailView`, as is the row around it
(`.safeAreaInset(edge: .top)` over `secondaryBackground.opacity(0.8)` +
`.regularMaterial`, `HStack(spacing: .sm)`, `.lg` / `.sm` padding).

## 2. Signed out, the bookmark greys instead of disappearing

It had been hidden when saving wasn't possible, on the reasoning that a control
which cannot act shouldn't be offered — the same call the Follow button makes.
The owner reversed it: the row changing shape depending on who is looking is
worse than a dimmed control.

- `chromeCapsule` gained an `enabled` flag dimming the glyph to `tertiaryText`
  while keeping the fill and the 44pt frame.
- **⚠️ The disabled colour has to be stated explicitly.** The glyph names
  `primaryText` itself, and SwiftUI's `.disabled()` will not dim a colour a view
  sets for itself — a plain `.disabled()` would have left it looking active.
- **`canSave` was doing two jobs** — "signed out" *and* "this list is already
  yours" — and was split. Your own list still draws no bookmark, because saving
  a list you own means nothing and a permanently-greyed control there is a
  question with no answer.
- Two things followed from the decision rather than being asked for, each one
  line to undo: the menu's Save item is disabled rather than absent, and
  `toggleSaved` guards on `canSave` so "disabled" is enforced by the action.

## 3. The page is a slide-up layer now

It was the last top-level screen still pushing onto whichever nav stack you came
from — which is exactly why it wore a back chevron while tour detail and the
place page wore an X. New **`TourListPresenter`** (twin of the tour, maker and
place presenters, `performDismiss` included) and a fourth `BottomLayerController`
in `ContentView`.

**What a new layer needs, all of it:**

1. A presenter with `performDismiss`, wired once in `ContentView`, so the X
   collapses the layer itself rather than depending on an observer in a window
   the layer covers.
2. A `BottomLayerController` and an `.onChange` block that presents it **with
   the full environment chain re-injected** — the UIKit layer inherits nothing.
3. `.environment(listPresenter)` added to **every other layer's** chain, or a
   list row inside one of them is a silent dead control.
4. Its line in **`isAnyLayerPresented`** (bars go edge-to-edge so the layer
   can't show through the island's 8pt gaps) **and** in **`tabSelection`** (a tab
   tap tears it down). The place layer shipped missing from one in 1.1 (69) and
   the other in 1.1 (73).
5. Injection into the **bottom-module window** as well as the content window —
   that second window is where the tab teardown lives.

**⚠️ Two routing decisions, both conservative on purpose:**

- **A list row on a maker page pushes in-stack when that page is itself inside a
  layer.** `openList` mirrors `openPlaceFromMap` exactly, for its exact reason:
  presenting asks an `.onChange` in the covered main window to run, which is the
  dead place pin (#532). Slides up from a tab root, pushes from inside a layer.
- **"Go to creator" pushes in-stack** rather than stacking a maker layer over the
  list, so the layer is wrapped in its own `NavigationStack` the way the maker
  layer is. Tour detail reaches a creator the same way.

The empirical record worth keeping, because the two look contradictory: the
place page presents the **tour** layer from inside its own layer and that has
shipped fine; the maker page presenting the **place** layer from inside a layer
was dead on 1.1 (69)/(70). Until that difference is understood, follow the
conservative pattern for anything new.

**A shared `/l/` link now takes the same layer instead of its own sheet**, so
there is one copy of this screen with one way out, and `SharedListPresentation`
is deleted. Its prefetched items were never passed to the view — which loads
them itself — **so the sheet's one advantage did not exist.** CLAUDE.md's
session-94 note explaining the sheet is marked superseded in place rather than
left to be re-read as current.
