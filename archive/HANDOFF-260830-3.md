### 🔴 `check-image-duplicates.py` CACHES A FAILED FETCH AND THEN REPORTS IT AS A DUPLICATE, FOREVER

Found by running `--pins` on this batch. It reported one ERROR — **`rosewood-mayakoba-rwmayakoba_hero.webp`
and `the-old-cinema-chiswick-dreamspaces_hero.webp` sharing bytes**, two pins from earlier batches
that have nothing to do with each other. **It is a false alarm, and the catalogue is fine**: the two
live files hash `7c22f2dc…` and `3c82de46…`, plainly different, and after purging those two cache
entries the run comes back **`OK — no suspicious duplicates`** over all 254 pin images.

**The cause is in `fetch_hash`.** It shells out to `curl -sL` with **no `-f`, no HTTP-status check
and no image-decode check**, and rejects a response only when `returncode != 0` or the body is
empty. So **any non-empty error body — a 404 page, a CDN error page, a rate-limit page — is hashed
as though it were the image and written to `.cache/image-dupes/`**, where it is trusted by every
later run. Two different URLs that fail the same way become a byte-identical "duplicate" that never
goes away.

Here both cached entries held `27927b33ebee49d7…`, which is **neither file and not the Pages 404
page either** (`b6205073…`) — some transient response served while the deploy for this batch was
still propagating.

⚠️ **This is the script's own founding bug inverted.** It was rebuilt in session 103 because it
printed *"OK — no suspicious duplicates"* having fetched nothing at all; it now cannot report a
false pass, but it can report a **false alarm that persists**. **The fix is small and belongs in
`fetch_hash`**: pass `-f`, check the status, and refuse to cache anything Pillow will not decode.
**✅ FIXED THE SAME SESSION, on owner instruction (*"fix the checker"*).**

`download()` now writes the body with `-o` and reads the status with `-w "%{http_code}"`, so **a 200
is the only success**; the verdict is the pure `download_verdict(returncode, status, data)` so the
selftest can pin it offline. `looks_like_image()` must then pass before anything is hashed — a
format signature (`has_image_signature`) and, with Pillow, a real decode. **Nothing failing any of
those is cached.** 🔴 **`has_image_signature` is pinned by its own test because it is the only guard
when Pillow is absent**, which a fresh container always is; the whole selftest was re-run with `PIL`
blocked to prove that path. 🔴 **The cache directory moved to `.cache/image-dupes-v2/`** — a poisoned
entry is indistinguishable from a good one, so the old ones simply stopped being read; one refetch
per machine, once, and nothing at all in a fresh container.

**Proven by breaking it: 7 injected fault classes, 7/7 caught.** Against the live host a real 404
returns `HTTP 404, 9379 bytes` and writes **0** cache entries while a real image still hashes.
**`--pins` on a cold v2 cache: 254 images, 254 cached, `OK`** — the false alarm cannot be
reproduced. `--maker MAD` still reports its 3 documented INFO groups and exits clean.
