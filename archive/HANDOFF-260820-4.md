The right answer to the question in brackets was: no reason, only age.

## The fix was to delete the second screen

`LikedListView` was written before the list page was rebuilt on the place page
(#547) and never followed it — system nav bar and title, plain rows, no hero
carousel, no GALLERY / MAP strip, no brass count. After #553 it was also the
only list still pushing in from the side.

Restyling it would have produced two screens that must be kept looking alike,
which is precisely the arrangement that produced the gap. So Liked now renders
through **`TourListDetailView`** itself, selected by a new **`TourListTarget`**
(`.list(id:preloaded:)` / `.liked(ownerName:tourIds:)`) — the `MakerView.mode`
pattern. `LikedListView` is deleted.

**The join that made this cheap: `TourListItem.id` IS the tour id.** Liked's
contents are ordinary items with no note, built from `LibraryStore` in saved
order, so rows, carousel, map, count, layer presentation and the maker-page
in-stack fallback are all one shared, untouched path. Look for that trick
before building a parallel one.

Liked reads the store on **every body evaluation** rather than fetching once,
so un-saving a tour anywhere removes the row with no refresh, and it never
shows the loading spinner.

## The two absences, and why they are structural

- **No bookmark.** `saved_journeys.journey_id` is a foreign key to
  `journeys.id`. Liked has no such row — which is exactly what lets it work
  signed out. Nobody can save Liked, ever, so it is **absent rather than
  greyed**: the signed-out bookmark #553 dims is a temporary state, this is a
  permanent fact.
- **No `…`.** Every item in that menu acts on a `journeys` row: share, rename,
  make visible, delete. Liked is permanent by construction (owner decision
  2026-07-27). An empty menu, or one of permanently-greyed items, says less
  than no menu.

## 🔴 Owner decision — do not re-propose

> "i cannot bookmark someone's like list?" … "leave it"

You cannot, and it stays that way. Three options were weighed:

1. **Make Liked a real `journeys` row per user.** Saving comes free, and so do
   share links — but it breaks signed-out saving (journeys need auth) and the
   rule that un-saving is the only way to lose a save, and needs a migration of
   every existing user's library.
2. **A `saved_user_liked` table** keyed on the owner rather than a list id.
   Genuinely small — the `liked_tour_ids(p_user)` RPC already exists. Rejected
   because it re-creates a second keep-a-person concept beside Follow, which is
   **the exact duplication PR #398 deleted** on owner instruction: *"just have
   one, which is follow and not bookmark."*
3. **Nothing** — Follow already means "keep track of this person", and their
   Liked is on their profile.

An offered middle path (a Follow item in the `…` on someone else's list, which
the tour page already has) was not taken either.

## Two bugs this turned up

- **🐛 `deleteList` called SwiftUI's `dismiss()` — a leftover from #553 that
  shipped in TestFlight 1.1 (94).** Inside a UIKit modal that does nothing, so
  deleting a list left the layer on screen over a list that no longer existed.
  It calls `close()` now. **When a screen becomes a layer, sweep every
  `dismiss()` in it** — the X was converted and this path was missed.
- **CI caught a compile error, which is the argument for opening the PR before
  the build.** `listId` became optional when Liked joined the screen and six
  list-only writes still passed it raw to `TourListService`. All six sit behind
  the `…` menu or edit mode, so the guards now state at the type level what the
  UI already implied. **Grep the whole build log for `error:`** — the failure
  summary at the tail names the file and never the reason.
