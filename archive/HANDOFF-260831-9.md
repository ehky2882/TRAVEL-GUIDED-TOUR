## 🔴 THE THREE DURABLE FACTS

### 1. Adding a version for review LOCKS ITS SCREENSHOTS. It does not lock its text.

Deleting a screenshot on a version in `READY_FOR_REVIEW` returns:

    409 STATE_ERROR — "Can't Delete Screenshot while Ready For Review appScreenshots"

**Nothing in the DOM says so** — the file inputs are not `disabled`, the fields are not `readOnly`,
and the only visible hint is that the thumbnails render dimmed, which they also do on a perfectly
editable version. So the browser gives you no signal until Apple refuses.

**The order that avoids this: do screenshots BEFORE `Add for Review`.** If you are already past that
point, the sequence is remove the version from the submission → replace → re-add. It costs nothing
but time, and the submission survives it.

**⚠️ Text metadata is NOT locked in that state.** `description` and `promotionalText` both PATCHed
`200` while the version sat in `READY_FOR_REVIEW`, so there is no need to pull a version out of a
submission to fix copy. Only assets.

### 2. `promotionalText` DOES NOT INHERIT between versions — and it fails silently.

Version 1.1.1 was created from 1.1. The description carried over. The screenshots carried over.
**`promotionalText` came back `None`**, while the live 1.1 page had one.

Submitting as it stood would have **blanked the promotional line on the live store page** with no
warning anywhere. Nobody reads that field; it would not have been noticed.

**Check `promotionalText` on every new version record.** It is also the ONE field Apple lets you edit
on a live app **with no submission**, which makes it the right home for anything timely — it now
carries the catalogue size and can be bumped the day a city lands.

### 3. The standing "nine IAP tiers are missing review screenshots" note is WRONG on both count and cause.

Measured this session across all 14 tiers:

- **`images = 0` on every single one**, including the three Apple has already **APPROVED**
  (0.99, 1.99, 12.99). A review screenshot is therefore **not** what gates these products.
- Only **one** tier was `MISSING_METADATA` — `tour.tier.999` — and the difference from its healthy
  neighbours was that it had **no `inAppPurchaseAvailability` record** (404 on that relationship,
  where 8.99 returns one). Its localization, price schedule and review note were identical.

⚠️ **Availability was created to match the other thirteen** (all 13 shared exactly one configuration:
`availableInNewTerritories: true`, 175 territories) **and the state did not clear.** The owner then
added an image in the UI and it flipped to `READY_TO_SUBMIT`. **The image, not the availability, is
what unblocked it** — the availability gap was real and needed fixing regardless, but do not record
it as the cause. What actually gates an IAP here is still not fully characterised.

# ADDENDUM 2026-09-01 — Apple REJECTED it, and the cause was structural

**Guideline 2.1(b) — Information Needed.** Apple could not locate eleven of the twelve submitted
items: *"we cannot locate the In-App Purchases, such as Premium Audio Tour (Tour Tier 2.99) …"*

**They were right, and it is not a bug.** Measured against the live catalogue:

    priceTier 99   -> 66 tours   (all multi-stop walks)
    priceTier NULL -> 1,487 tours
    tiers 2.99 … 19.99 -> ZERO tours

**The eleven tiers were attached to nothing, so there was no purchase path to find.** The reviewer
followed the App Review notes exactly, reached the $0.99 walks the notes describe, and correctly
reported that the other eleven products did not exist in the app.

## 🔴 THE STRUCTURAL LESSON: A TIER IS ONLY REAL ONCE CONTENT USES IT

Under the creator-set pricing model, a tier becomes purchasable only when a maker picks it. Banking
the whole ladder up front therefore **fails review by construction, every time.** Submit each tier
**as it comes into use**, not in advance.

**⚠️ AND THE "OPTIONS FOR CREATORS" ARGUMENT IS TRUE IN DESIGN AND FALSE IN THE BUILD.** The owner
proposed arguing the chicken-and-egg: creators cannot choose prices until the tiers are approved.
Sound in principle — but **`MakerTourService` writes `priceTier: nil` on every maker-created tour and
there is no pricing UI.** Phase 4 has not shipped. A reviewer accepting the argument would ask to see
where a creator picks a price and find nothing, which is a worse rejection than the first.

**The chicken-and-egg is NOT tiers ↔ content. It is tiers ↔ the pricing UI.** Approving tiers today
would not give creators options, because there is no screen to choose them on.

**⚠️ AND DEFERRING COSTS NOTHING** — once a version is live, further tiers can be submitted **on their
own, no build, ~a day**. There is nothing to bank. Do not hold an app release hostage to them.

**⚠️ PRICING TOURS TO SATISFY REVIEW WAS CONSIDERED AND REJECTED.** The catalogue's biggest walk is
20 stops / 27 min; a ladder to $19.99 has nothing to stand on, and pricing-then-reverting shows Apple
prices dropping the day after approval. ⚠️ **The owner's counter — that price should reflect QUALITY,
not length — is correct**, and my length-based ladder was the wrong frame for a creator platform. It
does not change the conclusion, because the blocker is the missing UI, not the missing content.

## 🔴 MY ORDERING MISTAKE: REPLY TO APPLE **BEFORE** CANCELLING A SUBMISSION

Removing items from a reviewed submission is impossible — `409 STATE_ERROR, "Item was already
submitted"`. So the route is **cancel → new submission**. `PATCH {canceled: true}` works on a
submission in `UNRESOLVED_ISSUES` (it returns `CANCELING`, then `COMPLETE`, shown as *Removed*).

**But cancelling CLOSES the message thread's reply box.** Apple's message survives and is readable;
the compose field is gone. Their explicit request — *"please reply to this message"* — can then only
be answered through **Contact Us**, or not at all.

**Reply first, then cancel.** Cost here: the reply was never sent. Mitigated by putting the
explanation in **App Review Information → notes**, which the next reviewer reads before starting —
arguably the better home anyway, since a thread on a dead submission may never be opened.
