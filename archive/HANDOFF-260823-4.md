## The bug, in one line

**A failed request does not mean we do not have the photograph.**

`App.init` gives `URLCache.shared` **200 MB of disk**, so a photograph scrolled
past before is on the phone. But **gh-pages serves images with
`Cache-Control: max-age=600`** — ten minutes later iOS insists on revalidating
with the server before it will use those bytes. With no signal there is no
server, `URLSession` throws, and `HeroImageView`'s `catch` was a comment saying
*"placeholder stays"*. The phone threw away a photograph it already had.

## The fix

`Data/OfflineImageFallback.swift`: on a failed fetch, read
`URLCache.shared.cachedResponse(for:)` directly — a lookup no freshness rule
stands in front of. Wired into **both** fetch paths: `HeroImageView` and
`LaunchImageWarmup` (so the first screenful is warm offline too).

- **🔴 IT MUST STAY TIED TO AN ACTUAL FAILED REQUEST.** The shortcut that looks
  equivalent — `.returnCacheDataElseLoad` on the request — is worse: it prefers
  the stored copy on a perfect connection too, so a photograph we later
  **replace** never updates. The catalogue does replace them (the
  Thyssen-Bornemisza hero was the wrong building for a month; Milan's castle
  hero was swapped for the facade its script describes) and those corrections
  have to reach people. **Owner accepted the narrow trade-off on exactly that
  basis** (2026-08-23): offline you may see a superseded photograph until you
  are back on signal.
- **⚠️ Cancellation is deliberately NOT worth falling back on.** A view scrolled
  off screen cancels its own fetch; nobody is waiting on a photograph for a
  screen that has gone, and consulting the cache there is work on every row of
  a fast scroll. Both `CancellationError` and `NSURLErrorCancelled` are
  excluded; every other error consults the cache, including unrecognised ones
  (better a photograph we have than a grey box).
- **⚠️ The tests never touch `URLCache.shared`** — it is process-wide state a
  test has no business mutating. They build their own cache in a temp
  directory, and one stores a response with `max-age=0` to pin the actual
  point: the fallback ignores freshness entirely.

## A content rule this forces, now written into CLAUDE.md § Image Pipeline

**🔴 CORRECTING AN IMAGE MEANS A NEW FILENAME — never overwrite bytes at a live
URL.** A phone that has downloaded a tour reads its photographs off its own disk
and never asks the server again, and the fallback above serves whatever
`URLCache` holds for a URL — so bytes swapped underneath an unchanged URL reach
neither. Someone who downloaded a tour would keep the wrong photograph until
they deleted and re-downloaded it, which nobody would think to do.

**This is not hypothetical: the Thyssen hero was corrected exactly that way**,
in place at the same URL, and that fix would not have reached a downloaded tour.
A new filename is a new address, so every phone fetches it automatically.

The heavier alternative — having downloaded tours re-check their photographs on
wifi — is deliberately NOT built. The filename rule costs nothing and needs no
machinery; revisit only if replacements become frequent enough to forget.
