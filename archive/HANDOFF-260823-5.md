## A. The fullscreen video viewer — specced, NOT built

Today a clip renders letterboxed inside the **320pt landscape carousel box**
(`Components/GalleryVideoView.swift`, mounted at `TourDetailView.swift:333` and
`PlayerView.swift:213`). A 9:16 clip uses **180pt of a 345pt box** — about half
of it is black.

### 🔴 Two traps that will each cost a build if missed

1. **Present it from `BottomModuleRoot`, not the tour sheet.** The mini-player
   and tab bar live in a window at `windowLevel = .normal + 1`
   (`Components/BottomModuleWindow.swift`) and paint over ordinary modals.
   **Session 24 hit exactly this with `PlayerView`** — hiding the module around
   the transition made it worse, and presenting from that window was the fix.
   Drive it from shared state the way `showingFullPlayer` already is.
2. **Suppress the inline view's `resumeNarrationIfNeeded()` while fullscreen is
   up**, or the tour's narration starts playing *behind* the video. It fires
   from three places (`GalleryVideoView.swift:120-131`) and presenting a cover
   trips at least one. Let the fullscreen view own the takeover, keeping the
   existing rule: a clip **with** audio pauses narration and resumes on
   dismiss; a **silent** clip never touches it — the silent path is live today
   and must keep working.

### The expand affordance

**A corner button, NOT the surface tap** — the surface tap is already
play/pause (`GalleryVideoView.swift:114`), and playback starts from an explicit
`Button` so it lands in the accessibility tree. Build the expand control the
same way, so VoiceOver reaches it and it does not claim the horizontal drag the
carousel needs for paging.

### 🔴 Rotation: measured, and the obvious approach was rejected

The app is **portrait-locked** — `UISupportedInterfaceOrientations~iphone` is
`UIInterfaceOrientationPortrait` alone. At real dimensions:

| | Size | vs carousel |
|---|---|---|
| 4:3 in the carousel today | 345 × 259 | — |
| 4:3 fullscreen, upright | 393 × 295 | **1.3×** |
| 4:3 fullscreen, rotated | 524 × 393 | **2.3×** |
| 9:16 in the carousel today | 180 × 320 | — |
| 9:16 fullscreen | 393 × 699 | **4.8×** |

**Fullscreen transforms vertical and barely helps landscape** — which matters,
because the one real video in the catalogue is 1200 × 900 and the whole image
pipeline is 4:3.

**Real device rotation was considered and rejected.** `Info.plist` is a
ceiling: a view controller can only *narrow* the declared orientation set, so
allowing the viewer to rotate means opening rotation **app-wide** and then
locking every other screen back. There is **no `AppDelegate`, no scene delegate
and no orientation handling anywhere** in the project — pure SwiftUI lifecycle
— so that machinery would have to be introduced. Worse, **orientation belongs
to the window scene, not the window**: the viewer presents from the secondary
`PassThroughWindow`, which shares its scene with the main window, so a real
rotation also rotates the map, drawer and tour sheet behind the video.

**✅ Chosen instead: rotate the video, not the app.** The app's orientation is
never touched, so nothing outside this one view can regress.

- Fullscreen stays portrait. A **landscape** clip's content stack renders
  through `.rotationEffect(.degrees(90))` at 852 × 393, centred.
- **Rotate on the real device orientation, not unconditionally.**
  `UIDevice.current.orientation` and `orientationDidChangeNotification` still
  report physical orientation while the app is portrait-locked
  (`beginGeneratingDeviceOrientationNotifications()`), so the clip sits upright
  until the phone is actually turned. Without this it opens sideways.
- **Controls rotate with the video** — a rotated frame with an upright close
  button reads as broken.
- **Vertical clips never rotate.** 9:16 is already 393 × 699 upright; turning it
  sideways makes it smaller. Same as TikTok, Reels and Shorts, which letterbox
  landscape and never rotate — YouTube rotates because it is landscape-native.
- Accepted trade-off: status bar and home indicator stay portrait-aligned.

**⚠️ Detect shape from the DISPLAY size, not `naturalSize`.** Phone-shot video
is commonly 1920 × 1080 natural with a 90° `preferredTransform` — reading
`naturalSize` alone calls a vertical clip landscape and rotates it the wrong
way. Apply `preferredTransform` first. The async track load already exists in
`GalleryVideoView.prepare()` (used for `hasAudio`) and is where this belongs.

### What the simulator can and cannot judge

`test_sim` covers the layout, the expand button, carousel paging, the bars not
painting over it, and the narration pause/resume. **Rotation is device-only** —
the simulator rotates the *interface*, which is precisely the thing this design
deliberately does not do.

**Also worth a look on device:** whether the clip's audio actually pauses the
tour narration. That path has never run, because the only prior video is silent.

## B and C — planned, and NOT blocked by A

An earlier draft of this plan said both were "largely pointless until video
displays properly." **That was an overstatement.** Link pins open a browser and
never touch the video viewer; creator import produces tours whose video shows in
the existing carousel. A makes both better; neither waits on it. **They can run
in parallel with the viewer work.**

### B. Link pins — someone else's post as a map pin

**A link pin should BE a tour**, one whose audio is a link instead of a file.
Three facts make "everywhere tours go" cheap rather than prohibitive:

1. **`TourKind` is only `==`-compared, never exhaustively switched**
   (`Models/Tour.swift:4-7`, ~20 sites) — adding `case link` compiles
   everywhere untouched.
2. **All 6 `stop.audioURL` readers already guard it**
   (`TourDownloader.swift:102`, `ProximityMonitor.swift:242`,
   `PlayerView.swift:721`, `TourDetailView.swift:577` and `:1447`,
   `GroupListenCoordinator.swift:331`) — making it optional is mechanical and
   compiler-checked.
3. **Duration 0 already means "no audio"** — `TourAuthoringView.swift:37`
   defines `hasAudio` as `totalDurationSeconds > 0`.

**Platform facts, tested 2026-08-18:**

| Platform | oEmbed, no key | Thumbnail |
|---|---|---|
| **TikTok** | ✅ 200 | **576 × 1024 vertical**, plus caption and author |
| **YouTube** | ✅ 200, Shorts work | ⚠️ **480 × 360 landscape even for Shorts** |
| **Instagram** | ⚠️ **unresolved** | — |
| **LinkedIn** | not tested | no known public oEmbed |

**⚠️ The one open question:** whether Instagram's oEmbed needs a token. A
tokenless call returned a *media-level* error, not an auth error, which suggests
it works — Meta's docs still say App Review and business verification, while
reports say Meta reversed that on 15 June 2026. **One real public post URL
settles it in thirty seconds.**

Owner decisions: looks like a tour on map and cards, **detail page credits the
source**, **filterable** via a format chip beside the existing Walks chip; no
writing of the owner's own; thumbnail **re-hosted cropped to 1200 × 900**;
opens in **`SFSafariViewController`** (a real Safari process, so the platforms'
web players perform properly). **Link pins forced free** — a tour you do not own
must never carry a price.

### C. Creator import — the stated top goal

*"I want to remove the hurdle."* **Not deferred, just not exercisable yet** —
the app is not in the App Store, so the owner is necessarily the only content
source today. Build it ready for launch rather than after.

**The mechanism needs no model change.** `audioURL`, `audioDurationSeconds` and
`heroImageURL` are non-optional and validator-enforced, but all three are
derivable from a video file: the audio track via `AVAssetExportSession`, a
poster frame via `AVAssetImageGenerator`, the duration from the asset. A posted
clip is a short single-stop tour whose narration is the video's own soundtrack,
and the player, geofence, downloader, lock screen and paid gating all keep
working.

**Order: camera roll → share extension → web bulk.** Camera roll needs no new
Xcode target and the owner is its first user. The share extension is what
creators actually want, and it is where B and C converge — **the iOS share sheet
hands over a URL from TikTok/Instagram and a file from the camera roll**, so one
extension branches on the payload: URL → link pin, file → hosted clip. It needs
its own target and bundle ID; `testflight.yml` and the fastlane `beta` lane both
assume a single target.

**⚠️ Never build a paste-a-link importer** — fetching media server-side breaks
the platforms' terms and stored links rot.

**Two things that will bite:** a video re-downloaded from TikTok has its
**location metadata stripped**, so confirming the pin is mandatory; and **music
in a reel is licensed for that platform, not for resale in a paid app**, so the
creator needs an explicit keep / mute / record-over choice plus an attestation.
**`NSPhotoLibraryUsageDescription` is absent from `Info.plist`** and is needed
for any camera-roll path.

## Process notes

- **`Tours.json` round-trips byte-identically** under
  `json.dumps(indent=2, ensure_ascii=False)` plus a trailing newline. Verifying
  that before editing kept the diff at **46 insertions, 0 deletions** on a
  1,467-tour file. Always check first.
- **NYC key order is not canonical** — there are **7 distinct key orderings**
  across the 100 NYC tours. Match a neighbouring tour rather than assuming one
  house order. NYC also uses `triggerMode: "manual"` at radius 30, unlike the
  newer cities' `geofenced`.
- **The NYC maker id is a sequential placeholder**
  (`00000000-0000-0000-0000-000000000001`), not a uuid5 like the newer city
  makers. Do not mint one for it.
- **iCloud share links (`share.icloud.com/photos/…`) cannot be fetched here** —
  they redirect to a JS app that pulls media through Apple's private API after
  load. Chat attachment remains the only reliable transport, as with Dropbox
  Transfer links in session 78.
- `git push --force-with-lease` failed with **"stale info"** for a branch that
  did not exist on the remote at all. Fetch first and check before reaching for
  force.
