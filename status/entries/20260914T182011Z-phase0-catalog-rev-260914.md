# Phase 0: the seed stops rewriting the whole catalogue on every run

_2026-09-14 18:20 UTC · branch `phase0-catalog-rev-260914`_

Phase 0 of `docs/delta-catalog-fetch-design.md`, built and tested. Backend only —
no app code, no payload change, no App Store release.

**The bug, reproduced against a throwaway Postgres carrying the real schema and
the real catalogue:** an IDENTICAL re-seed rewrote **3,745 of 3,745 tours, 424 of
424 makers, 303 of 303 places and all 4,117 stops.** `seed_from_toursjson.py`
ended every upsert with `updated_at = now()` unconditionally, and `stops` had no
`updated_at` at all and was deleted and re-inserted per tour on every run.

**After:** the same re-seed writes **zero rows across all four tables**, verified
both by timestamp and by `xmin` (the physical row version), and `max(tours.rev)`
does not move.

**What landed:**
- `backend/catalog_rev.sql` — new, additive, idempotent, self-verifying. One
  sequence, `rev` on tours/makers/places, `updated_at` on stops, triggers that
  move `rev` only on a real change, and a stop edit bumping its parent tour.
- `backend/seed_from_toursjson.py` — the `set` list and the `where` guard are now
  generated from ONE list per table, so they cannot drift apart when a column is
  added. Stops are upserted rather than deleted and re-inserted.
- `backend/test-seed-idempotence.sh` — new regression test. **Verified it fails
  when the guard is removed**, not just that it passes when present.

**Two findings worth keeping:**
- `stops_tour_id_order_key` had to become DEFERRABLE. Counter-tested: with it
  non-deferrable, inserting a stop mid-walk fails the seed with a duplicate key
  violation. Row-by-row upserts renumber transiently where the old
  delete-then-insert did not.
- `updated_at` is the wrong thing for a test to assert on for `stops`: the
  trigger declines to move it when content is unchanged, so a wasteful rewrite
  is invisible to it. The test checks `xmin` as well.

Also corrected `docs/lessons.md`, which still carried the wrong **8.2%** figure
for `longDescription` (#891 fixed `CLAUDE.md` but not this) — it is **43.9%** —
along with the method that produced the error (`gzip.compress` defaults to level
9; PostgREST serves level 1) and the heading, which had the generalisation
backwards for prose.
